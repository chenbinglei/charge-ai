# 充电运营平台业务规则基线 v2

## 2. R-AUTH：权限与数据范围

1. 平台超级管理员由 IOT 平台管理，拥有 P1 全页面、全租户、全数据范围。
2. 单租户 P1 用户由 IOT 管理，只能看到 IOT 授予的该租户页面、站点、设备和数据；后端以租户范围强制过滤。
3. M3 的运营商用户、角色、页面和场站数据范围由 P1 管理；场站商家即运营商/租户，IOT 仅提供租户主档与资产同步。
4. 企业管理员在 P1 创建、停用企业用户；P1 维护 P2/M2/M4 的企业角色、页面及企业/组织/车队/账务数据范围。
5. 企业用户可使用本企业所有车队车辆，但不因此拥有车队资金、角色或配置权限；具体页面能力仍由 P1 授权。

## 3. R-ASSET：设备能力

1. IOT 负责设备接入和实际通信能力；P1 负责设备业务能力档案，并与 IOT 实际能力校验。
2. 业务能力至少包括：是否可获取可信 VIN、是否支持按金额启动并自动停充、是否支持屏幕强制启动、屏幕 VIN 鉴权、屏幕刷卡启动。
3. 余额、电卡、车队固定金额和无 VIN 先充后付启动只能在“按金额启动/自动停充”能力有效的设备上开启。

## 4. R-PERSON：个人用户、会员与个人余额

1. 个人用户是独立主体；会员只是可选权益，未办会员、未充值的预付用户必须完整保留用户、订单、退款、发票和客服记录。
2. M1 公共充电不要求绑定车辆、VIN 或车辆认证；扫码识别枪，登录会话识别个人。
3. 个人余额启动前必须冻结启动金额；页面显示平台/场站默认金额，用户可在个人可用余额内调整。
4. 个人外部预付支付成功后才允许启动；结算按订单快照扣款并原路退还差额。

## 5. R-FLEET：企业、车队、车辆和限额

1. 企业可建立多个车队；一辆企业车辆只能属于一个车队，VIN 在企业内唯一。
2. 所有企业用户可使用企业所有车队车辆，以支持临时换班；不以用户所属车队限制充电。
3. 车队配置：固定单笔启动金额、金额限额、可用场站范围、日/月周期。金额限额是用能控制，不等于授信。
4. 企业预存资金可锁定分配至车队；增加、降低或回收分配金额时，必须扣除已冻结订单和已划拨电卡余额后再重算可释放资金。

## 6. R-FUND：企业资金、充值和授信

1. 企业资金账户包含预存余额、冻结金额、已用授信和可用授信；企业是资金、对账和发票主体。
2. 企业充值到账先自动偿还已用授信，余款才增加企业预存可用余额。
3. 正常 VIN 匹配企业充电必须以企业预存及车队锁定资金保障；企业预存不足时不得启动。
4. 企业授信仅适用于“企业用户 M2 扫码 + 设备未获取 VIN + 企业开启先充后付”的例外。
5. 无 VIN 先充后付启动前，原子校验：`企业预存可用余额 + 剩余授信 ≥ 企业无 VIN 默认单笔金额`；未开启、设备不支持金额控制或校验不足均拒绝启动。
6. 无 VIN 订单结束后，如 VIN 上报且命中企业车队、未上报或不命中，均先扣企业预存余额，不足部分占用授信；后两类必须标记车辆核验异常。

## 7. R-CARD：企业电卡

1. 电卡资金所有权属于企业；卡余额从企业预存余额经车队划拨并锁定，是独立的真实子余额。
2. 电卡在任一时刻只能归属一个车队，可授权多名企业用户使用；跨车队只能走转卡流程，不得并行归属多个车队。
3. 电卡必须配置单笔启动金额。刷卡或 M2 绑定电卡启动前，原子校验卡状态、卡可用余额、卡冻结、车队金额/站点/日月限额和企业账户状态；任一不满足即拒绝启动。
4. 启动时冻结电卡单笔金额并下发至桩；订单上报后扣实际金额、释放余额。多人共用卡必须防止并发重复冻结和重复扣款。
5. 电卡不使用企业授信进行充值或启动；卡余额不足不得以授信替代。

## 8. R-START-PERSONAL：个人扫码启动

1. 顺序为：扫码识别枪 → 登录用户校验 → 价格/权益试算 → 个人余额冻结或外部预付成功 → 下发金额启动 → 桩自动停充 → 订单结算。
2. 个人可选择外部支付、个人余额、会员权益、券/红包/积分；不出现企业账户、电卡、企业车辆或授信。
3. 未绑定车辆不得阻止公共充电。

## 9. R-START-ENTERPRISE：企业扫码启动

1. M2 使用企业账号登录，不展示个人支付、个人余额或员工手工预充金额。
2. 设备获取可信 VIN 且 VIN 属于企业任一车队车辆时，按该车队固定单笔启动金额下发；同时校验车队资金、金额限额、可用站点和日/月周期。
3. 设备未获取 VIN 时，不需员工选择车辆或车队；仅在企业开启先充后付且满足 R-FUND 第 5 条时，按企业无 VIN 默认单笔金额下发。
4. 企业余额、车队资金、金额限额或站点范围不足时，M2 拒绝启动并提示联系企业管理员；不允许降级为个人支付。
5. 企业用户以绑定电卡方式启动时，遵循 R-CARD，不使用企业无 VIN 授信规则。

## 10. R-VIN：VIN 核验与订单追溯

1. VIN 来源分为设备可信上报、设备缺失、人工维护、不可用；手工选择车辆不等于可信 VIN。
2. M2 无 VIN 启动后的最终订单上报 VIN 时，平台校验其是否在企业任一车队；命中则归属对应车队，不命中/缺失则标记异常。
3. VIN 异常订单必须在订单、企业账单、企业对账和报表中关联企业用户、VIN、车辆（如有）、车队（如有）、资金流水和异常原因。

## 11. R-EXCEPTION：屏幕启动与异常结算

1. 屏幕强制启动不自动指定企业资金主体。订单上报 VIN 后，平台在该站点可服务企业中查找匹配车辆；命中则按该企业资金账户结算。
2. 强制启动订单无 VIN 或 VIN 未匹配任何可服务企业时，生成“异常未结算订单”，不得自动扣任一企业账户；由授权人员配置结算主体后人工结算并审计。
3. 屏幕 VIN 鉴权启动时，VIN 必须命中站点可服务企业的车队车辆；命中后按车队固定金额启动，不命中即鉴权失败、不允许启动。
4. 屏幕刷卡启动遵循 R-CARD；订单上报后从卡余额扣实际金额。

## 12. R-ORDER：订单与资金一致性

1. 每笔订单固化价格、权益、支付渠道、资金主体、启动金额、设备能力、企业先充后付开关、VIN 核验状态和规则版本快照。
2. 冻结、启动指令、回执、订单上报、扣款、解冻、退款、人工结算均使用业务唯一键和幂等控制。
3. 启动失败、超时、取消或设备未启动必须自动解冻；停止或订单上报延迟时保持待结算，禁止重复扣款。
4. 车队分配、电卡回收/挂失不得侵占充电中订单的冻结金额。

## 13. R-PAYMENT、R-REG、R-OPS、R-DASHBOARD

1. 支付支持多个微信与支付宝商户/应用、银联及第三方支付；支付路由按运营主体、场站、应用和订单类型确定，并固化订单快照。
2. 监管采用“省市监管档案 + 映射 + Outbox 上报任务 + 回执 + 自动重试 + 人工补推 + 对账”模型，详见现役《[省市监管接入与可靠上报设计 v1](../../../docs/integrations/省市监管接入与可靠上报设计-v1.md)》。
3. 运维中心只做 IOT 同步告警的业务处置、工单与受控指令；不配置 IOT API、协议、Topic 或原始告警规则。
4. D1 独立部署、只读展示；布局、指标、主题和发布在 P1 管理，访问按已发布配置和 IOT/P1 授权校验。
