> 审查对象：《充电运营平台 12 周全功能交付实施计划 v2.0》
> 审查日期：2026-08-12
> 交叉参考：《公司级总体架构说明 v1》《工程架构与数据分库设计 v1.3》《工程架构评估处置 v1》《万台单机架构收敛与高可用演进决策 v1.1》

## 一、遗漏内容

### 1.1 团队规模与角色配置

**问题**：全文未定义开发团队人数、角色分配和责任矩阵。§8 仅要求"每日可确认业务规则的产品/业务负责人"，但未说明后端开发、前端开发、测试、DevOps 各多少人。

**影响**：无法判断"并行推进"的实际并行度。如果只有 1 名后端开发 + 1 名前端开发，6 服务 + 7 端的并行是不可能的；如果有 6 名后端（每服务 1 人）+ 4 名前端 + 2 名测试，可行度完全不同。

**建议**：在 W1 开工评审前明确团队组成，并按服务/前端分配责任矩阵。

### 1.2 数据库表级 DDL 设计与评审

**问题**：W1 写"10 schema Flyway 入口"，但 10 个 schema 包含数十张表（`evco_iam` 的用户/角色/权限/会话/审计、`evco_trade` 的订单/会话/费率/价格快照、`evco_finance` 的账户/分录/冻结/结算/对账等）。"Flyway 入口"是迁移目录结构，不是表设计。

**影响**：W3 `master` 模块开始编码时，如果表结构未设计评审通过，开发要么等设计、要么自行猜测——后者导致 W4-W5 大量返工。

**建议**：W1 增加"10 schema 核心表 DDL 设计与评审"工作项；评审通过后冻结基线，后续变更走 Flyway 迁移评审。

### 1.3 Outbox 中继机制的实现时间

**问题**：架构评估处置 v1 §1 已采纳"单机使用服务内小批轮询，`SKIP LOCKED`、Kafka 确认后标记、允许重复投递"。处置 v1 §3 已采纳"各 schema 独立 Outbox，DLQ 亦按生产领域隔离"。这意味着 **每个有跨服务事件需求的 schema 都需要独立的 outbox 表 + 轮询中继 + DLQ 处理**。计划全文未为此分配实现时间。

**影响**：Outbox 中继是订单→资金、平台→设备控制等跨服务事件链路的"发动机"。如果到 W5 开发订单模块时才发现中继未实现，要么临时用同步调用绕过（破坏架构约束），要么阻塞订单开发。

**建议**：W2 分配"Outbox 中继框架（`SKIP LOCKED` 轮询 + Kafka 发送 + 标记 + DLQ）"的实现时间，作为 P0 工程跑道的一部分。

### 1.4 指标目录治理体系

**问题**：架构设计 v1.3 §4.2.2 要求"指标目录新增或将 SPARSE 提升为 CORE 必须经过容量评估、JSON Schema/契约版本测试、DDL 迁移和回填方案评审"。P0 的 telemetry-service 列了"指标目录与存储模型"，但计划未说明这是否包含 CORE/SPARSE/DERIVED 三级分类规则、容量评估流程和升级评审机制。

**影响**：如果 W1 只建了空目录，W4 开始写分钟归并时需要决定哪些指标是 CORE（写入 ClickHouse 宽表）、哪些是 SPARSE（按需物化），没有治理规则会导致随意决策，后续改分类需要 DDL 迁移和数据回填。

**建议**：W1 明确"指标目录 v1"包含 CORE/SPARSE/DERIVED 分类规则和首批指标清单（至少覆盖设备状态、功率、电量、订单关联指标）。

### 1.5 WebSocket 推送体系的工程量

**问题**：架构说明 §6.1.2 定义了复杂的 WebSocket 模型：snapshot + 增量推送、`telemetry_subscription_ticket`（短时效、范围限定）、授权版本校验、按页面类型限制推送频率、断线重连刷新快照。计划 W4 仅写"WebSocket"一词。

**影响**：这不是一个简单的 WebSocket 广播，而是一个授权+订阅+增量+断线恢复的推送系统。按计划 W4 同时还要完成 Kafka 链路、Redis CAS、ClickHouse 归并、命令/回执、原文归档、告警——WebSocket 推送体系的工程量可能被严重低估。

**建议**：将 WebSocket 推送拆分为 W4（基础推送 + ticket 授权）和 W5（增量推送 + 断线重连）两个子任务。

### 1.6 凭据管理方案

**问题**：P0 integration-service 列了"凭据引用、模拟器"。架构说明要求"客户受控 KMS/HSM 或受控 Vault"。计划未定义开发环境用什么管理微信支付证书、IOT 同步签名等敏感凭据。

**影响**：W6 微信支付联调时如果凭据管理不规范（如明文放在 Compose 环境变量中），存在证书泄露风险；生产交付时凭据注入方式不统一也会导致部署问题。

**建议**：W1 定义凭据管理方案——单机可使用 Docker Secret + 环境变量模板 + MinIO 加密 Bucket 的组合，不引入 Vault 常驻进程。

### 1.7 API 版本化策略

**问题**：6 个阶段的开发中，API 会持续演进（P0 的 IAM API 在 P3 加企业权限、P4 加数据范围过滤）。计划未定义 API 版本化策略——是 URL 路径版本（`/v1/users`）还是 Header 版本？破坏性变更如何处理？

**影响**：前端 7 端在不同阶段开发，如果 API 无版本管理，P4 修改的 API 可能破坏 P2 开发的前端页面。

**建议**：W1 确定版本化策略；非破坏性变更在原版本内演进，破坏性变更使用新版本路径，旧版本保留至少 2 个阶段。

### 1.8 环境数据管理

**问题**：§6 定义了 dev/sit/alpha/beta/pilot/production 共 6 个环境。计划未定义各环境的数据来源和管理方式——sit 用什么数据？alpha 需要真实设备吗？pilot 的企业数据从哪来？production 的数据迁移怎么做？

**影响**：W8 "企业试点数据"和 W12 "试点数据迁移"都是一次性提及，没有定义数据准备、脱敏、校验的方法论。环境数据缺失会阻塞验收。

**建议**：W2 定义环境数据策略——dev 用种子数据；sit 用脱敏数据 + 模拟桩；alpha 接真实桩但不接真实支付；pilot 接真实支付但不开放公共用户。

### 1.9 架构评估 25 项风险的处置落实

**问题**：《工程架构评估处置 v1》定义了 25 项风险的处置决策（Outbox 中继、共享 Topic 拆分、Redis CAS 升级、ClickHouse 引擎、deployment_mode 一致性、EMQX 限速等）。计划中未引用这些处置，也未为关键项分配实现时间。

**影响**：评估处置是架构层面的"技术债清单"。如果不在计划中分配时间，交付团队可能不知道这些要求的存在，导致实现不符合架构决策。

**建议**：在计划 §4 的逐周表中，为关键处置项标注对应工作——如 W2 增加"Outbox 中继框架"、W3 增加"Redis Lua CAS 完整裁决键"、W4 增加"EMQX 连接限速配置"。

### 1.10 缺陷管理流程

**问题**：§5 提到"周四缺陷分级"，但未定义缺陷管理流程——用什么工具跟踪？缺陷等级如何定义（P0/P1/P2/P3 的标准）？谁负责分派？修复时限？回归测试流程？

**影响**：12 周项目预计产生数千个缺陷（基于规模估算）。没有缺陷管理流程，"未验收功能不得标记完成"无法执行。

**建议**：W1 确定缺陷工具（GitLab Issues 或 Jira）、缺陷等级标准和 SLA（P0 当日修复、P1 阶段内修复、P2 下阶段修复）。

### 1.11 代码审查机制

**问题**：计划要求"AI 承担主要执行工作"，但未定义 AI 生成代码的审查机制。§5 的"禁止后端全做完才做前端"是流程约束，不是质量约束。

**影响**：AI 生成的代码在跨服务一致性、资金逻辑等场景可能有隐蔽错误。无审查机制则错误进入集成测试，修复成本放大。

**建议**：W1 定义代码审查规则——资金/订单/控制相关代码必须人类逐行审查；CRUD 和页面可抽检；审查记录纳入审计日志。

## 二、未完善的环节

### 2.1 阶段 No-Go 后的处置方案

**问题**：§6 定义了每个里程碑的 Go/No-Go 决策点，但从未定义 No-Go 之后做什么。如果 R1（W4）No-Go，W5 是继续 P2 还是修复 P1？如果 R2（W6）No-Go，W7 是继续 P3 还是修复 P2？

**影响**：No-Go 决策无配套行动方案，实际执行中要么"带着已知缺陷进入下一阶段"（缺陷累积），要么"停下来修复但后续全部顺延"（计划失控）。

**建议**：为每个 No-Go 场景定义 3 种处置选项：(a) 修复延期——后续阶段顺延 N 天；(b) 范围裁剪——从当前阶段删除非关键功能；(c) 降级部署——部署部分功能，剩余进入下阶段。

### 2.2 §7 验收标准缺乏量化定义

**问题**：§7.1-7.3 全为定性描述："菜单均有已验收的页面"、"重复回调不造成重复扣款"、"通过性能测试"。未定义量化标准。

**不完善处**：
- "已验收"由谁判断？标准是什么？
- "性能测试"——什么指标？什么阈值？P95 < 多少 ms？
- "安全扫描"——SAST？DAST？依赖扫描？OWASP Top 10？
- "积压恢复"——72 小时积压的恢复时限是多少？
- "空环境恢复演练"——恢复 RTO 是多少？

**建议**：§7 增加量化验收标准表——功能完成率 ≥ 95%、严重缺陷 = 0、订单 P95 < 500ms、ClickHouse 查询 P95 < 3s、MySQL 恢复 RTO < 2h、ClickHouse 恢复 RTO < 4h、Redis 重建 < 5min、单元测试覆盖率 ≥ 70%。

### 2.3 §5 并行机制的"需求提前一周"是隐性串行瓶颈

**问题**：§5 要求"阶段前一周"产出《阶段详细需求包》。但产品负责人同时要验收当前阶段（周四集成测试、周五领导演示），又要细化下一阶段需求——这是双倍工作量集中在同一个人身上。

**不完善处**：如果产品负责人在 W4 验收 R1 时无法同时细化 W5 的需求，W5 开发第 1 天没有契约可开工。计划没有定义"需求细化延迟"时的应对措施。

**建议**：增加 backup 产品负责人；或将需求细化改为"持续澄清"模式——产品负责人每日参与 30 分钟开发答疑，需求文档标注"已确认"和"待确认"，待确认部分用 Mock 先行开发。

### 2.4 文档与培训材料的时间线

**问题**：W12 才提及"培训"和"运维手册"。7 端的用户手册、API 文档、运维 Runbook、部署指南如果都挤在 W12，与 UAT 缺陷修复和上线部署竞争时间。

**不完善处**：架构说明 §8 要求"每个服务具备 Runbook"。但计划中 Runbook 仅在 W12 出现，没有分阶段编写计划。

**建议**：每阶段交付时同步编写该阶段的 Runbook 和用户手册章节；W12 仅做整合、校验和培训演练。API 文档由 OpenAPI 自动生成，W1 起持续维护。

### 2.5 D1 大屏的开发跨度

**问题**：D1 从 P1（W3 实时数据接口）开始，跨 P2（W5 订单/营收接口）、P3（W7 企业/租户指标接口）、P4（W9 专题/布局/发布），到 P5（W11 V2G 专题与压测）——**跨度 9 周，始终处于"部分完成"状态**。

**不完善处**：D1 没有独立的验收节点。P1-P3 的 D1 工作只是"接口"，P4 才做"专题、布局、发布"——意味着 D1 的实际开发集中在 W9-W10 的 2 周内（4 个专题 + 布局 + 发布），与 W9 的营销/工单/分析/小程序发布争抢资源。

**建议**：D1 前序阶段仅预留数据接口（telemetry-service 和 platform-service 提供），D1 前端开发集中在 P4；或在 P4 验收时将 D1 降级为"数据接口就绪、前端在 Phase 2 交付"。

### 2.6 测试策略的分阶段引入

**问题**：§7.3 要求"通过权限隔离、安全扫描、契约测试、全端 E2E、目标环境性能测试、Kafka 积压恢复和空环境恢复演练后，方可生产上线"。但这些测试集中在 W11，没有分阶段引入计划。

**不完善处**：
- ArchUnit 架构测试：应在 W1 建立 6 服务骨架后立即引入，而非 W11
- 集成测试：应从 W3（首个业务模块 master）开始
- E2E：应从 W4（首个完整链路：设备→MQTT→遥测→展示）开始
- 性能测试：应从 W6（首个交易链路）开始，而非 W11
- 安全测试：应从 W2（IAM/认证/权限）开始，而非 W11
- 积压恢复测试：应从 W4（首个 Kafka 链路）开始

**建议**：§5 的并行机制表中增加"测试引入"行——每阶段必须引入的测试类型和通过标准。

## 三、潜在风险点

### 3.1 W1 工作量严重超载

**风险**：W1 要完成——6 服务 Maven 骨架、10 schema Flyway、OpenAPI/MQTT/事件契约、Docker Compose（6 服务 + MySQL + Redis + Kafka + ClickHouse + EMQX + MinIO + Prometheus + Grafana + Nginx）、CI 流水线、初始化脚本、部署模式锁定、IAM、菜单/角色种子数据、7 端登录壳和公共包。

**量化**：仅 Docker Compose 的资源调优（cgroup 限制、内存上限、磁盘水位、healthcheck、启动顺序）就需要 1-2 天。6 服务的 Maven 多模块结构（每服务 parent + bootstrap + interfaces + application + domain + infrastructure）也需要 1-2 天。7 端前端公共包（ui + api-client + types + design-tokens）需要 1-2 天。加上 CI、契约、IAM、初始化——**W1 的工作量是 2-3 周的量**。

**影响**：W1 延迟直接导致 R0（W2 验收）推迟，连锁影响后续所有阶段。

### 3.2 W4 遥测管线是技术密度最高的周

**风险**：W4 要完成——Kafka 消费链路、Redis Lua CAS（完整裁决键 `(source_time, source_sequence, received_at, event_id)`）、ClickHouse 分钟归并（CORE/SPARSE/DERIVED 模型）、WebSocket 推送（snapshot + 增量 + ticket 授权 + 断线重连）、命令/回执、原文 MinIO 归档、告警事件、协议证据链、查询权限与审计。

**量化**：其中 Redis Lua CAS 完整裁决键是架构评估处置 v1 §8 的强制要求；ClickHouse 分钟归并涉及 CORE/SPARSE/DERIVED 三级分类和 argMin/argMax 语义；WebSocket 推送涉及 ticket 授权和增量推送。这三项各自需要 2-3 天，合计已超 W4 的 5 天容量。

**影响**：W4 遥测管线是后续所有阶段的基础设施（订单关联指标、企业投影、报表导出、大屏全部依赖分钟数据）。W4 延迟或质量不达标将连锁影响 W5-W11。

### 3.3 W6 微信支付 + 资金 + 对账 + M1 全链路挤在一周

**风险**：W6 要完成——finance-service 个人账户/分录/冻结/释放/结算、integration-service 微信下单/回调验签/原路退款/渠道原文审计、支付/订单/资金幂等与对账、M1 支付/充电中/结束/订单/钱包/退款页面、R2 Beta 真实测试商户验收。

**量化**：仅微信支付的幂等设计（重复回调、重复报文、设备离线、补单）就需要 2-3 天。资金冻结/释放/结算的分录逻辑需要 2-3 天。M1 的 5 个页面（支付、充电中、结束、订单、钱包/退款）需要 3-5 天。三者并行也超过 W6 的 5 天容量。

**影响**：W6 是"交易试运行"的关键节点。如果支付或资金闭环不完整，R2 Beta 无法验收，W7 企业功能开发被迫在"支付不稳定"的基础上进行。

### 3.4 W9 营销全域 + 工单 + 停车 + 小程序发布 + 分析挤在一周

**风险**：W9 要完成——告警→工单→SLA、定时策略执行与控制审计、会员/券/红包/积分/活动/预算/精准营销/消息、停车/门禁/道闸业务映射、小程序内容/发布/灰度/公告通知、多维实时/历史分析与导出。

**量化**：营销全域（会员 + 积分 + 券 + 红包 + 活动 + 预算 + 精准营销 + 消息）是 8 个子系统，任何一个都不简单。仅积分系统就涉及积分获取规则、积分账户、积分核销、积分过期、积分对账。W9 的工作量至少是 3-4 周的量。

**影响**：W9 延迟导致 R4（W10 Pilot）验收范围缩减。如果营销功能未完成，R4 演示只能跳过营销模块。

### 3.5 W11 V2G 全链路 + 全量测试挤在一周

**风险**：W11 要完成——V2G 授权/策略/放电会话/订单/收益账户/放电价格/结算/提现/计量/风控/监管数据，同时执行全量 E2E + 安全 + 性能 + 积压恢复 + 备份恢复 + 回滚演练。

**量化**：V2G 本质是"反向充电平台"——独立状态机、独立计费模型、独立资金流、独立监管通道。V2G 的计量还涉及双向电量差分和 `meter_epoch` 生命周期管理。V2G 全链路的开发量不亚于 W5-W6 的充电订单+支付链路。

**影响**：V2G 和全量测试争抢 W11 的 5 天，大概率两者都做不完整。V2G 不完整则 R5 RC 验收范围缩减；全量测试不完整则生产上线存在未验证风险。

### 3.6 外部依赖的关键路径未标注

**风险**：§8 的必要投入表列出了外部依赖的最晚时间，但未标注哪些在关键路径上。

**关键路径分析**：
- 微信测试商户（W3）→ W6 支付验收 → R2 Beta → 后续所有交易功能
- MQTT 模拟器/真实桩（W2）→ W3-W4 设备链路 → R1 Alpha → 后续所有设备功能
- IOT 同步签名/样例（W3）→ W3 协同模式 → R1 Alpha → 后续协同模式功能
- 企业试点数据（W7）→ W8 企业端 UAT → R3 Beta+
- Linux 服务器/独立数据盘/离机备份（W8）→ W11 恢复演练 → W12 上线

**影响**：如果任何一个关键路径上的外部依赖延迟 1 周，对应阶段的验收直接失败。计划没有为关键路径上的外部依赖定义"最晚启动时间"（比"最晚到位时间"更早）。

### 3.7 双模式（独立/IOT 协同）的测试覆盖

**风险**：§7.1 要求"独立模式允许平台维护资产；IOT 协同模式仅接收 IOT 同步并禁止越权修改"。但计划中每个阶段的功能开发是否 **两种模式都测试**，未明确说明。

**影响**：如果 W3 的资产 CRUD 只在独立模式测试，W4 验收时 IOT 协同模式的只读投影和写入拦截可能存在未发现的缺陷。双模式测试意味着每个功能的工作量翻倍——计划未反映这一成本。

### 3.8 10 schema 跨服务 Flyway 迁移的顺序依赖

**风险**：6 个服务各自管理自己的 schema 迁移，但服务间存在逻辑引用（如 `evco_trade` 的订单引用 `evco_master` 的设备 ID、`evco_finance` 的冻结引用 `evco_trade` 的订单 ID）。如果迁移顺序不当，服务启动时可能因表结构不匹配而失败。

**影响**：每次部署（R0-R6）都需要执行迁移。如果迁移顺序不稳定，部署可能失败，阻塞验收。

**建议**：W1 定义迁移策略——按服务启动顺序执行（gateway → platform → finance → integration → device-connectivity → telemetry）；跨 schema 使用逻辑引用（不建物理外键）；CI 中增加迁移顺序校验。

### 4.2 测试时间全集中在 W11 是结构性错误

**当前分配**：
- W1-W10：各阶段"并行测试"（主要是单元测试和阶段内集成测试）
- W11：全量 E2E + 安全 + 性能 + 积压恢复 + 备份恢复 + 回滚演练
- W12：UAT 缺陷修复

**问题**：
- 性能测试在 W11 才做——如果发现 ClickHouse 写入跟不上万台设备（50 亿行/年设计假设），修复涉及表结构和物化视图重设计，不可能在 W12 完成
- 安全测试在 W11 才做——如果发现 IAM token 撤销有漏洞，修复涉及 gateway + platform-service + finance-service 三服务联动
- E2E 在 W11 才做——7 端 × 数百个页面的 E2E 测试用例编写和执行至少需要 2 周

**合理分配**：
| 测试类型 | 应开始时间 | 计划时间 | 偏差 |
|---|---|---|---|
| ArchUnit | W1 | 未明确 | 缺失 |
| 集成测试 | W3 | 各阶段 | 合理 |
| E2E | W4（首个完整链路） | W11 | **延迟 7 周** |
| 性能测试 | W6（首个交易链路） | W11 | **延迟 5 周** |
| 安全测试 | W2（IAM） | W11 | **延迟 9 周** |
| 积压恢复 | W4（首个 Kafka 链路） | W11 | **延迟 7 周** |
| 备份恢复 | W2（首个迁移后） | W11 | **延迟 9 周** |

### 4.3 V2G 的时间分配

**当前**：W11 的 5 天中，V2G 与全量测试争抢时间。V2G 实际可用开发时间估计 2-3 天。

**V2G 的实际工作量**：
- V2G 授权（车辆/设备能力校验、合同管理）——2 天
- V2G 策略（放电功率曲线、时间窗口、电网响应）——2 天
- 放电会话/订单（独立状态机）——2 天
- 独立收益账户（与充电资金隔离）——1 天
- 放电价格与结算——2 天
- 双向计量（正/反向有功电量差分，meter_epoch）——2 天
- 风控（SoC 限制、放电深度、异常检测）——2 天
- 监管数据——1 天
- **合计：约 14 天（3 周）**

**结论**：V2G 需要 3 周开发，计划分配 2-3 天。偏差达 5-7 倍。

### 4.4 营销全域的时间分配

**当前**：W9 的 5 天中，营销与工单/停车/小程序发布/分析争抢时间。营销实际可用时间估计 1.5-2 天。

**营销的实际工作量**：
- 会员体系（等级、权益、升级规则）——2 天
- 积分系统（获取规则、账户、核销、过期）——2 天
- 优惠券（创建、发放、核销、过期）——2 天
- 红包——1 天
- 活动（创建、报名、参与）——2 天
- 预算（预算池、消耗跟踪）——1 天
- 精准营销（人群标签、推送）——2 天
- 消息通知——1 天
- **合计：约 13 天（2.5 周）**

**结论**：营销全域需要 2.5 周开发，计划分配 1.5-2 天。偏差达 6-8 倍。

### 4.5 每阶段"可部署版本"的集成成本未计入

**问题**：6 个阶段每 2 周产出一个可部署版本（R0-R5），每次部署涉及：Flyway 迁移执行、配置校验、健康检查、进程替换、冒烟测试。计划未为"部署本身"分配时间。

**影响**：每阶段的部署+冒烟测试至少需要 0.5-1 天。6 次部署累计 3-6 天——相当于 1 周以上的时间未计入计划。

### 4.6 需求细化与开发并行的时间冲突

**问题**：§5 要求"阶段前一周"细化需求。但"阶段前一周"是当前阶段的开发周——例如 W2 要细化 W3-W4 的需求，同时 W2 本身有开发任务（网关/IAM/7端公共包）。

**影响**：产品负责人在 W2 的工作量 = W2 开发验收 + W3-W4 需求细化。这是双倍负载。如果产品负责人不是全职，需求细化质量下降；如果是全职，当前阶段验收参与度不足。
