## 1. 目的与使用边界

本清单收录不应在本轮菜单评审中直接落地、但会影响后续完整平台能力的优化事项。它不是一期、二期排期；待菜单、功能、规则和流程评审通过后，再按客户、设备能力、合规条件与商业优先级立项。

当前明确不纳入范围：云快充 1.6 等外部设备接入及其接口配置。该类接入由 IOT 平台负责，运营管理平台仅消费经过 IOT 标准化后的资产、能力、状态和订单事件。

## 2. V2G 调研结论与建议

### 2.1 国内实践的共同特征

国家层面已将车网互动纳入试点与规模化应用方向，强调双向充放电、标准、价格机制与示范验证；国家发展改革委后续组织了车网互动规模化应用试点，山东亦有入选项目。公开示范通常以园区、车队、可控双向设备和聚合调度为主体，而非任意公共桩、任意个人车辆的无差别放电。[国家能源局政策文件](https://zfxxgk.nea.gov.cn/2023-12/13/c_1310758710.htm) [国家发展改革委试点通知](https://www.ndrc.gov.cn/xwdt/tzgg/202409/t20240910_1392927.html) [试点项目清单](https://www.ndrc.gov.cn/xwdt/tzgg/202504/P020250402326784022659.pdf)

地方示范也在探索双向桩、聚合响应和结算，但设备双向能力、车辆授权、电网/负荷聚合方协议、计量与收益结算均是前置条件，而不是普通充电订单的简单扩展。[广州市工业和信息化局相关报道](https://gxj.gz.gov.cn/zt/dlys/tpxw/content/post_10840972.html) [广汽集团车网互动实践](https://www.gacgroup.com/cn/news/detail?baseid=19025)

### 2.2 对本平台最适合的路径

建议采用“先预留能力、后企业园区试点、再扩展聚合服务”的路线，当前不新增 V2G 菜单：

| 路径 | 适用性 | 建议 |
| --- | --- | --- |
| 有序充电 / 需求响应 | 可作为未来所有站点的通用调度能力 | 先在 IOT 与策略模型中预留设备能力、功率和时段事件，不改变当前用户菜单。 |
| 企业车队、园区 V2B / 需求响应聚合 | 最适合本平台的首个 V2G 商业化场景 | 车辆、车队、站点、资金和责任主体清晰，可控性高；应以签约企业、指定双向设备、指定车辆和指定站点为准入边界。 |
| 面向公众个人用户的 V2G / 虚拟电厂聚合 | 暂不适合作为首期通用能力 | 需解决车辆兼容、授权撤销、SOC 保底、用户补偿、双向计量、电网协议、收益分账与争议处理，不能混入普通公共充电流程。 |

因此，当前 V4.0 菜单中不增设“V2G/放电管理”。未来若立项，应以独立能力包实现，默认关闭并按租户、企业、站点、设备、车辆和合同逐级启用，避免影响既有充电、订单和资金闭环。

### 2.3 V2G 立项前置条件

1. IOT 已能识别双向设备能力，并稳定上报/执行充放电方向、功率、SOC、故障、计量和停止指令；运营平台不直接对接设备协议。
2. 企业、车辆及车主完成放电授权；车辆需同时满足双向能力、可用 SOC 下限和授权有效期。
3. 已明确与电网、园区能源管理方或负荷聚合商的调度责任、数据接口、结算周期、违约与争议规则。
4. 充电电量、放电电量、服务费/补贴、损耗补偿、税票与收益分配采用独立计量与账本，不复用普通充电订单的单一计费口径。
5. 配置安全兜底：SOC 下限、离场时间、用户紧急退出、设备故障安全停止、调度超时、人工审批和完整审计。

### 2.4 未来独立能力包建议（仅建议，不新增当前菜单）

| 能力域 | 后续能力 | 原因 |
| --- | --- | --- |
| 准入 | 双向设备、可参与站点、授权车辆、企业合同 | 防止不兼容车辆或无授权用户参与。 |
| 调度 | 可用容量预测、SOC 保底、邀约/接受、执行计划、紧急退出 | V2G 是可中断的能源服务，不能视同普通充电。 |
| 计量结算 | 充/放双向计量、补贴/服务费、企业/车主收益分配、对账单 | 保障财务与税务口径独立且可追溯。 |
| 风控合规 | 授权留痕、调度审计、异常补偿、监管/聚合方报送 | 控制资金、车辆使用权和电网响应责任。 |

## 3. 不改变当前菜单的优化事项

| 编号 | 优化事项 | 原因与建议 | 触发条件 |
| --- | --- | --- | --- |
| N-01 | 页面字段字典与原型 | 当前菜单已给出边界，但评审通过后需把每页查询条件、字段、按钮、校验、空态、导出与审批动作固化为原型/字段字典。 | 菜单评审通过后 |
| N-02 | 菜单—场景—规则—验收追踪矩阵 | 解决“菜单有名称、但无法验收”的问题；每个三级菜单至少关联角色、场景、规则、事件和验收用例。 | 详细设计前 |
| N-03 | 资金账本与日切核算设计 | 企业总预存、车队锁定、电卡锁定、订单冻结、授信占用和人工调整须采用不可覆盖流水与可对账余额。 | 财务模块开发前 |
| N-04 | 异常订单工单与责任时限 | 强制启动无匹配 VIN、订单补报、监管漏推、停车协同失败等需规定责任人、时限、升级和关闭证据。 | 运营规则评审时 |
| N-05 | 多支付渠道路由验收 | 统一验证多微信/支付宝、银联与第三方支付的商户路由、回调幂等、退款、对账和故障降级。 | 支付接入前 |
| N-06 | 监管适配包 | 对每个省市建立参数密文托管、字段映射版本、Outbox、重试、补推、回执和对账模板；不得把入网密钥写入需求文档或页面。 | 新省市接入前 |
| N-07 | 场站协同适配包 | 停车减免、门禁开门、闸机抬杆等按站点/租户启用，补充第三方失败重试、人工处理和隐私最小化。 | 有对应项目需求时 |
| N-08 | 离线与设备能力治理 | 对离线刷卡、金额自动停、VIN 获取、屏幕强制/VIN/刷卡启动等设备能力建立真实设备矩阵与灰度准入；无能力不得展示或下发。 | IOT 能力模型稳定后 |
| N-09 | 数据脱敏与职责分离 | 财务、退款、人工结算、导出、企业隐私数据应实行最小权限、复核、审计和脱敏策略。 | 安全评审前 |
| N-10 | 合作方与应用市场深化 | 泰安需求包含合作方与应用市场，但通用平台应先明确合作方数据边界、计费模式、结算对象和扩展应用生命周期。 | 生态业务立项时 |

## 4. 当前评审的建议顺序

1. 先评审《菜单架构》：确认每个应用的边界、一级/二级/三级命名与归属。
2. 再评审《功能详细说明》《业务规则基线》《场景与流程图集》：确认能否覆盖个人、企业、现场、财务、监管和异常闭环。
3. 对有争议的事项登记到本清单，避免在未确认设备能力、合同或监管约束前把功能写入当前菜单。
4. 评审通过后补齐 N-01、N-02 的原型、字段字典、追踪矩阵和验收用例，并保持同一需求基线版本。
