## 2. R-AUTH：身份、权限、数据范围与审批

1. IOT 是平台超级管理员、P1 租户 Web 用户、租户/站点/设备/枪数据范围的唯一权威源。
2. P1 是企业用户、企业角色、P2/M2/M4 页面权限和 M3 用户、角色、页面、场站业务范围的权威源；不得复制 IOT 运营端角色。
3. 企业成员身份使用企业成员关系，而不能仅用手机号判断；一个人可同时拥有个人车主身份、多个企业成员身份和运营商员工身份，所有令牌须包含当前应用、租户、企业成员与授权版本。
4. 企业用户可使用企业所有车队车辆，但仅默认查看本人订单；是否可查看企业汇总、资金、电卡或车队配置由企业角色决定。
5. 远程控制、告警确认、工单关闭等设备动作必须同时满足：`业务动作权限 ∩ IOT 租户/站点/设备范围 ∩ 设备实时能力`。
6. 退款、余额调整、车队划拨、电卡划拨、授信调整、人工结算、红冲、批量控制和敏感导出采用经办—复核—执行职责分离；不得自批。
7. 权限回收、离职、停用后应立即使相关会话失效并回收电卡使用授权；保留历史订单和审计。

## 3. R-ASSET：主数据与设备能力

1. IOT 管理租户、站点、设备、枪、接入协议、通信、遥测、原始告警和 API；运营平台不提供 IOT API、Topic、协议或密钥配置页面。
2. P1 维护业务启用策略，并消费 IOT 同步的设备能力；业务启用不得超过 IOT 实际能力。
3. 与订单相关的能力至少包括：可信 VIN 获取、按金额启动/自动停充、屏幕强制启动、屏幕 VIN 鉴权、刷卡启动、离线交易/补传和协议版本。
4. 不支持按金额启动/自动停充的设备不得开放个人余额、企业车队固定金额或电卡余额启动，避免结算超额。
5. VIN 只在个人/企业车辆菜单维护；订单仅保存 VIN、来源、核验结果与快照，不在订单侧维护车辆主档。

## 4. R-PERSON：个人用户与个人充电

1. 微信手机号授权的个人均建立个人用户档案；会员、个人余额、券、红包和积分均为可选附属能力。
2. 公共充电不强制绑定车辆、VIN 或车辆认证。扫码定位枪，登录会话识别个人，车辆仅作可选增强资料。
3. 个人余额启动前先冻结启动金额；默认金额可由平台/场站给出，个人可在可用余额内修改。外部支付必须预付成功才可启动。
4. 订单结算按价格、权益、支付和资金快照执行；余额按实扣款后释放余冻，外部预付按原渠道退差额。
5. 退款时按原资金来源拆分退回；会员、券、红包、积分返还规则必须由营销规则固化并留流水。

## 5. R-FLEET：企业、车队、车辆与 VIN

1. 一个企业可有多个车队；一辆车辆、一个 VIN 同时只能归属一个车队。
2. 企业用户无需选择车队或车辆即可在 M2 充电；设备可信 VIN 命中后，平台按车辆所属唯一车队进行费用和资金归集。
3. 车队策略包含固定单笔启动金额、金额限额、可用场站范围、日/月周期；车队是费用归集和资金控制单元，而不是企业用户的充电可用范围。
4. 企业用户必须具备企业资金充电资格、账号有效状态和可用站点资格；“可使用所有车队车辆”不能绕过这些基础校验。
5. VIN 来源须区分设备可信上报、设备缺失、人工维护、不可用；人工选择车辆不视为可信 VIN。

## 6. R-FUND：企业资金、冻结、授信和充值

1. 企业资金账本至少区分：企业未分配可用/冻结余额、车队可用/冻结余额、电卡可用/冻结余额、已用/可用授信。各层资金不得重复计入可用余额。
2. 资金路径固定为：企业未分配余额 → 车队余额 → 电卡余额 → 本次订单临时冻结；每一步形成可追溯的转账或冻结流水。
3. 企业充值到账先偿还已用授信，剩余部分才增加企业未分配可用余额。
4. 正常 VIN 匹配的企业充电，须按对应车队固定单笔金额冻结车队资金，并校验车队金额、站点与日/月限额。
5. 无 VIN 企业扫码仅在企业开启先充后付时允许。启动前校验：`企业未分配可用余额 + 可用授信 ≥ 企业无 VIN 默认单笔金额`；未开启或不足则拒绝启动。
6. 无 VIN 订单结束后，若 VIN 后补命中车队，则先按企业资金结算并进行企业未分配余额到车队成本归集；VIN 缺失或不匹配时标记异常，仍按企业预存优先、不足占用授信结算。
7. 强制启动订单未能自动归属企业时，不得自动扣款，必须进入异常未结算队列并经人工结算。

## 7. R-CARD：企业电卡

1. 电卡资金所有权属于企业；电卡同时只能归属一个车队，卡可授权多个企业用户使用。
2. 电卡余额由所属车队余额划拨形成，卡余额不再同时计入车队可用余额。
3. 电卡配置单笔启动金额。实际可下发金额取卡可用余额、卡单笔上限和车队剩余金额限额中的最小值；若小于最低启动保障金额则拒绝启动。
4. 刷卡或 M2 绑定电卡启动前，校验卡状态、授权用户、卡可用余额、卡冻结、车队站点/周期限额及企业账户状态；启动时冻结，结算后扣实并释放余冻。
5. 电卡不允许使用企业授信替代卡余额；卡挂失、转卡、转车队前必须结清冻结和未结算订单。离线刷卡、重复刷卡、黑名单同步和补传必须留作设备能力与订单异常规则。

## 8. R-START：六类启动方式

| 方式 | 前置校验 | 启动金额与资金 | 结果处理 |
| --- | --- | --- | --- |
| M1 个人扫码 | 个人会话、枪状态、价格与支付 | 外部预付成功或个人余额冻结 | 正常个人订单。 |
| M2 企业扫码且有 VIN | 企业账号、可信 VIN 命中车队、车队策略 | 冻结对应车队固定单笔金额 | 正常企业订单并归集车队。 |
| M2 企业扫码无 VIN | 企业开启先充后付、企业未分配余额+授信足额 | 企业无 VIN 默认单笔金额 | 订单后补 VIN；命中归集车队，否则标记异常。 |
| 桩屏 VIN 鉴权 | 可信 VIN 命中站点可服务企业车辆 | 冻结对应车队固定单笔金额 | 不命中即鉴权失败，不下发启动。 |
| 桩屏刷卡/M2 电卡 | 卡、用户、车队、站点和卡余额有效 | 冻结电卡单笔金额 | 按卡余额结算。 |
| 桩屏强制启动 | 无法事前确认资金主体 | 不事前扣企业资金 | 订单后按 VIN 归属；无归属进入异常未结算与人工结算。 |

## 9. R-ORDER、R-PAYMENT、R-SERVICE、R-REG、R-OPS

1. 每笔订单固化价格、权益、支付、资金、设备能力、VIN、车队、启动方式、规则版本和监管状态快照；历史订单不因后续配置变更重算。
2. 冻结、启动指令、设备回执、订单上报、扣款、解冻、退款、人工结算必须有业务唯一键和幂等控制。启动失败、取消、超时和未实际启动必须自动解冻。
3. 支付路由按运营主体、场站、小程序应用、订单类型和支付方式选择商户；多微信/支付宝、银联和第三方渠道均支持支付、退款、回调和对账。
4. 停车减免基于充电订单与停车订单的关联；厕所门禁基于“充电中订单/其他已配置权益”核验并形成授权与使用日志；道闸支持进出场、扫码授权和异常抬杆审计。
5. 监管按“档案—映射—Outbox 任务—回执—自动重试—人工补推—对账”处理；监管失败不阻断充电和资金结算，但必须形成合规待办。
6. 运维只处理 IOT 同步后的业务告警、工单和受控指令；高风险操作需审批、二次确认、审计和 IOT 回执。
