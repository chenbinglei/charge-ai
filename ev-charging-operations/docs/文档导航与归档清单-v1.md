# 充电运营平台文档导航与归档清单

> 版本：v2.4
> 更新：2026-08-20
> 用途：这是项目资料的**唯一导航入口**。先从这里判断“该读哪份、能否作为实施依据、历史资料在哪里”，再进入具体目录；它不替代需求、架构或交付基线。

## 1. 当前真实状态

- 仓库现役交付物包含 3 份管理汇报 DOCX、1 张架构 PNG，以及设备控制、退款、双模式和监管任务的版本化契约 Schema/状态机。W0 已产生七服务 Maven 无业务骨架、外部化配置、健康检查、共享基础能力和七项健康检查自动化测试；工程仍未产生业务源码、Flyway 迁移、部署编排或业务 API/E2E 证据。
- 所以“文档或 Schema 已定义”不等于“能力已上线”。真实监管、真实 V2G、万台容量和 RPO/RTO 必须分别通过 C3-R、另批现场试点、真实设备与目标负载/恢复演练门禁。
- 历史资料、审查意见和重复交付物均已保留在 `archive/`，但**不得**作为当前实现依据。

## 3. 按角色的阅读路线

1. 产品/验收：需求基线版本清单 → 菜单架构、功能详细说明、业务规则、场景图集 → v3 实施计划。
2. 后端：v3 实施计划 → 架构基线 v2 → Kafka 事件目录 → 服务 README → `delivery/execution/01` 的依赖与回归范围。
3. 前端/大屏：需求基线 → 架构基线中的同步 API 与 WebSocket 边界 → 已冻结的高风险 OpenAPI/MQTT 契约 → 对应应用 README。
4. 资金/支付/退款：业务规则基线 → Kafka 通俗说明 → 架构基线第 4 节 → Kafka 事件目录 → 高风险契约与状态机 → `finance-service` 与 `integration-service` README；不得以管理汇报图替代该链路。
5. IOT/遥测：架构基线 → Kafka 通俗说明 → Kafka 事件目录 → MQTT/OpenAPI 契约。
6. 国内监管：架构基线 → Kafka 事件目录 → [监管接入设计](integrations/省市监管接入与可靠上报设计-v1.md) → 监管与外部生态方案。虚拟电厂/第三方能源平台：只读后续扩展章节；不得提前创建外部协议、Topic 或消费者。
7. 管理汇报：`delivery/leadership-reports/` 的摘要材料；需要做技术或范围决策时，回到本表中的现役基线。

## 6. 后续维护规则

1. 一项事实只能有一个现役权威文件；其他文档仅链接并说明用途，不再复制规则或 Topic 表。
2. 新 Topic、消费组、服务边界、数据所有权或支付退款流程的变化，必须同步更新架构基线、事件目录和受影响服务 README，并记录在 [变更与审批日志](../delivery/execution/02-变更与审批日志.md)。
3. 文档被替代时，保留原文件并移至 `archive/`，在归档 README 写明日期、原因和现役替代文件；不删除历史证据。
4. 新增代码、DDL、契约或部署资产后，先更新其对应目录 README 和执行台账，再宣称该能力存在或可运行。
5. 现役资料按《[文档可读性与术语说明规范](standards/文档可读性与术语说明规范-v1.md)》补齐术语、责任、原因、失败处理与权威链接；归档历史不倒改。
