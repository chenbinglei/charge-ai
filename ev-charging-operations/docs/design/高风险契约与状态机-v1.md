# 高风险契约与状态机

> 版本：v1.1（W1 冻结）
> 依据：DEC-20260814-013。JSON Schema、MQTT 和 OpenAPI 是机器可读合同；本文定义跨合同的状态机、顺序和验收。任何字段或迁移变更必须走变更审批。

## 1. 冻结范围与权威文件

| 场景 | 机器可读合同 | 事实所有者 | 局部顺序键 |
| --- | --- | --- | --- |
| 设备控制 | `device-control-command.v1.schema.json`、`contracts/mqtt/` | `device-connectivity-service` 执行，`platform-service` 保存业务意图 | `deviceLifecycleId:connectorId` |
| 支付退款 | `finance-refund-request.v1.schema.json`、`high-risk-operations-v1.yaml` | `finance-service` | `originalPaymentTransactionId` |
| IOT 协同主数据 | `master-sync-command.v1.schema.json` | `platform-service.master` | `sourceSystem:externalId` |
| 监管任务 | `regulatory-task.v1.schema.json` | `ecosystem-service` | `targetId:businessType:businessId` |

Schema 位于 [`contracts/events/schemas/`](../../contracts/events/schemas/)，所有契约均为 `1.0`。实现必须以 JSON Schema 校验请求/消息；未知字段、错误大版本、未登记枚举或不满足状态转换的输入进入拒绝审计或所属业务模块 DLQ，不能“兼容性忽略”。

## 2. 设备控制状态机

```text
REQUESTED → AUTHORIZED → DISPATCHED → ACKNOWLEDGED → SUCCEEDED
                  │             │              └──→ FAILED
                  │             └──→ EXPIRED / DELIVERY_UNKNOWN
                  └──→ REJECTED
DELIVERY_UNKNOWN → QUERYING → SUCCEEDED / FAILED / MANUAL_REVIEW
```

- 创建时必须原子固化 `commandSequence`、`expectedStateVersion`、`authorizationSnapshotId` 和 `expiresAt`；同一枪仅接受严格递增序号。
- 执行者先校验未过期、序号未落后、目标状态版本匹配、设备仍属于当前生命周期，再允许 MQTT 发布。设备端也必须重复校验；不得依赖 Kafka 的“恰好一次”。
- 超时不是失败：状态为 `DELIVERY_UNKNOWN`，通过回执查询或设备状态核验裁决。重放同一 `deviceCommandId` 返回既有结果；相同幂等键而内容不同返回冲突。
- V2G 真实放电命令在当前版本恒为 `REJECTED(V2G_REAL_EXECUTION_CLOSED)`；模拟命令不得进入 MQTT 下行 Topic。

## 3. 支付退款状态机

```text
REQUESTED → ELIGIBILITY_CHECKING → PENDING_CHANNEL → CHANNEL_SUBMITTED
      │                │                    │                 └──→ COMPLETED
      │                └──→ REJECTED         └──→ CHANNEL_UNKNOWN
      └──→ DUPLICATE                            CHANNEL_UNKNOWN → RECONCILING → COMPLETED / FAILED / MANUAL_REVIEW
```

- 所有退款请求按**原支付交易**串行；数据库必须以原支付交易、累计退款额和状态版本进行条件更新，防止两个独立 `refundRequestId` 超额退款。
- `UNUSED_TOPUP` 只能恢复原资金批次且不生成租户结算调整；`CHARGING_ORDER_REFUND`、`PRICE_CORRECTION` 成功后才生成不可回写的结算调整请求。
- 外部超时、重复回调和查询结果不一致均为 `CHANNEL_UNKNOWN`，只能通过原渠道查询/对账或人工处置完成；不得新发一笔无原路由幂等保护的退款。

## 4. 双模式状态机

```text
UNINITIALIZED → INITIALIZING(independent | iot-collaborative) → LOCKED
LOCKED → REJECT_MODE_CHANGE
```

- `deployment_mode` 只在安装事务中写入一次；服务启动、网关策略、MQTT ACL、IOT 同步入口和健康检查读取同一不可变值。
- `independent` 拒绝所有 IOT 主数据同步；`iot-collaborative` 只接受白名单 IOT 的签名同步并拒绝平台侧平台/租户/资产写入。两种模式均由平台 IAM 作为最终授权决策点。
- 模式间迁移不是 API 操作：必须新建实例，完成离线迁移演练、资产生命周期重建、消息水位线核对和用户批准后才可切换流量。

## 5. 监管任务状态机与 C3-R

```text
PENDING_VALIDATION → PENDING_SEND → SENDING → SUCCEEDED
         │                 │             └──→ RETRYABLE_FAILURE → PENDING_SEND
         └──→ MANUAL_REVIEW                         └──→ MANUAL_REVIEW
MANUAL_REVIEW → PENDING_SEND / CANCELLED
```

- 任务唯一性为 `targetId + businessType + businessId + businessVersion + mappingVersion`；补推创建新尝试或关联任务，绝不覆盖失败证据或回执。
- W10 仅可标记为**监管内部就绪**：Schema/映射校验、模拟对端、漏推补推、任务/回执/对账和 P1/D1 投影均通过。
- 生产 Go 的 C3-R 对每个部署要求的监管目标分别留证：开户/白名单与网络、生产密钥引用、真实档案/状态/订单报送、有效回执和双方对账。任一必需目标失败即 No-Go。

## 6. 最小验收集

1. 同枪并发启停、延迟回执、过期命令和重复投递不会导致反向或重复控制。
2. 同一原支付交易的并发部分退款、重复回调、渠道超时和对账恢复不会超额退款或改写账本。
3. 两个部署模式均拒绝对方专属写入，并可由启动摘要与审计证明锁定。
4. 监管模拟成功不会满足 C3-R；真实目标的每类报送、回执与对账均能追溯至任务、映射和证据。
