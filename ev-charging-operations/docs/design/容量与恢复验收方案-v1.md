# 容量与恢复验收方案

> 版本：v1.0（W12 生产 Go 门禁）
> 原则：在真实设备和目标部署负载通过前，禁止使用“万台可用”、具体 RPO 或具体 RTO 作为销售、验收或上线结论。

## 1. 先冻结被测工作负载

验收方案必须记录并经用户确认：设备数、枪口数、实际厂商/协议、平均与最大消息字节数、最短/典型上报周期、在线连接、重连风暴、订单峰值、控制峰值、监管目标/频率、分析查询并发、导出量、保留年限、服务器与 NVMe 规格、离机备份目标和网络带宽。缺一项只可得出“实验结果”，不能得出容量承诺。

## 2. 强制压测与故障试验

| 场景 | 通过条件 |
| --- | --- |
| 真实设备 E2E | 至少一种目标桩/网关完成认证、遥测、订单、控制、断线、补传、计量与证书轮换。 |
| 常态与 3 倍突发 | 在目标消息负载和查询并发下，订单/资金/控制的 SLO 未越用户签署阈值；积压可在约定窗口清空。 |
| 重连风暴与乱序 | 限速、全抖动退避、幂等和局部顺序正确；无重复扣款、重复控制或错误状态回退。 |
| 资源压力 | ClickHouse merge、Kafka lag/OOM、Redis 重建、磁盘 70/85/90% 水位均按 Runbook 降级且关键链路保留。 |
| 灾难恢复 | 从空白主机和离机副本恢复 MySQL、ClickHouse、MinIO 关键对象；核对订单、账本、控制审计、监管证据和分钟遥测。 |

## 3. RPO/RTO 签发规则

RPO 取各数据域实测的最差值：备份/归档延迟、离机副本完成时间、上游可重放窗口和对象副本状态。RTO 取从故障声明到恢复服务、关键数据核对和业务放行的实测总时长。两者必须标注环境、负载、日期、负责人、失败项和适用边界；单机故障不承诺持续可用。

W12 只在完整报告、Runbook、演练录像/日志和用户签署的阈值同时具备时，允许把特定设备规模和 RPO/RTO 写入验收或合同。否则生产 Go 只能表述为“未签发容量与恢复承诺”。
