# 工程架构评估处置与服务边界调整

> 版本：v1.0  
> 日期：2026-08-12  
> 依据：[`archive/design/工程架构与数据分库设计三方专家批判性评估清单-v1.md`](../../archive/design/工程架构与数据分库设计三方专家批判性评估清单-v1.md)、当前 8 核 32 GB 单机约束，以及“独立/IOT 协同双模式”的既定边界。  
> 结论：采用 6 个 Java 部署单元；不在单机阶段部署 Nacos；补齐 Outbox、资金对账、指标目录、协议治理和恢复/诊断闸门。

## 1. 最终服务边界

| 服务英文名 | 主要职责 | 必须隔离的原因 | 不拥有/不允许做 |
|---|---|---|---|
| `api-gateway` | 七端 API 统一入口、令牌预校验、路由、限流、TraceId | 防止互联网流量直接冲击业务服务 | 对象级授权、订单和资金编排、MQTT。 |
| `platform-service` | IAM、主数据权威投影、企业客户、交易、营销、运营、V2G | 这些业务低频且同步协作密集，合为模块化单体可节省 JVM/RPC/运维成本 | 外部协议 I/O、资金账本、MQTT 长连接、分钟遥测。 |
| `finance-service` | 账户、不可变分录、冻结、结算、退款、对账、出款、发票事实 | 资金风险、审计和恢复优先级必须独立 | 任意余额直接改写、设备控制、第三方协议细节。 |
| `device-connectivity-service` | EMQX MQTT 上下行、统一设备报文校验/标准化/控制；仅协同模式的 IOT HTTP/HTTPS 管理同步入口 | 长连接、重连风暴、签名校验与外部 IOT 输入不能耗尽 Web/交易资源 | 直接写资产权威表、订单结算、资金事实。 |
| `integration-service` | 微信/支付宝/银联/银盛、银行/对公、监管、门禁/道闸、开票等适配器，含回调、重试、原文审计、映射和对账 | 慢调用、证书、厂商升级和失败重试与核心交易隔离 | 账本、订单状态机、页面权限、MQTT。 |
| `telemetry-service` | 状态合并、Redis 实时投影、分钟归并、ClickHouse 写入、曲线/大屏/分析查询 | 高频输入、批写和大查询不应影响资金、订单和配置 | 订单、资产、权限、资金写入。 |

### 1.1 IOT 资产同步为何不让设备互联服务直写资产表

“接口由哪个服务接收”与“谁是业务事实所有者”必须分开。`device-connectivity-service` 接收、验签、幂等、审计 IOT 推送，并在 `evco_device_connectivity.iot_management_sync_inbox` 落入原文摘要和处理状态；同事务写入 Outbox，发布 `evco.master.sync-command.v1`，由 `platform-service.master` 幂等应用并发布结果。API 仅在收件箱落库后返回“已受理”，IOT 以查询/回执确认最终结果。`platform-service` 是 `evco_master` 的唯一写者：独立模式接收本地管理操作，协同模式只接收来自该受控命令的变更。

若让两个服务直接更新 `station`、`charger`、`connector` 表，设备迁移、删除、字段优先级和生命周期就会变成跨服务竞争写入；这恰好会制造用户此前担心的资产错配问题。该划分既满足“设备数据接入和 IOT API 同一个服务”，也保持一份资产真相。

## 2. Nacos 决策

当前不部署 Nacos，也不在业务代码绑定 Nacos SDK。Docker Compose 内部 DNS 已能稳定解析六个固定服务名；版本化环境文件、启动前配置校验和网关静态路由足够支持单机交付。单实例 Nacos不能为单服务器创造高可用，反而增加一个 JVM、端口、账号、数据与恢复对象。Nacos 官方也将单实例定位为测试/单机试用，生产高可用使用集群。[Nacos 官方部署概览](https://nacos.io/en/docs/latest/manual/admin/deployment/deployment-overview/)

| 未来形态 | 服务发现与配置选择 |
|---|---|
| 当前单机 Docker Compose | Compose DNS + 版本化环境文件/密钥注入；不部署 Nacos。 |
| 多台 VM、非 Kubernetes | 当存在多副本、动态地址和动态配置的真实需求时，部署有认证、外部数据库、备份和演练的 Nacos 集群。 |
| Kubernetes | 默认 Kubernetes Service/DNS + ConfigMap/Secret；仅在跨集群动态配置或既有企业 Nacos 治理要求明确时再接入 Nacos。 |

服务发现不是领域能力。现在只要求所有服务外部化配置、健康检查和 HTTP/Kafka 契约稳定，未来采用 Nacos 或 Kubernetes 不会触发业务重写。

## 3. 多指标遥测模型

功率和累计电量只是两个例子。协议 `metrics[]` 的每个指标必须先进入全局受治理目录，记录 `metric_code`、对象层级、值类型、单位/倍率、量程、质量规则、语义类型、分钟归并规则、存储等级和版本。指标按三类入库：

1. `CORE`：跨站高频查询的标准量写入 `telemetry_minute` 宽列，并构建站/租户物化聚合；
2. `SPARSE`：厂商差异或低频诊断量写入类型化窄表 `telemetry_metric_minute`，按 `metric_code` 查询；
3. `DERIVED`：电量差值、负荷率、利用率、告警率、健康分等由受版本控制的计算产生服务表和聚合表。

这比“所有指标塞宽表”更能扩展，也比“每设备×每指标×每分钟一行”更能控制行数。新指标必须经过契约、容量、DDL/回填和查询模型评审；未登记指标不得静默进生产库。Redis 与 ClickHouse 都使用 `(source_time, source_sequence, received_at, event_id)` 的完整最后值裁决键。

## 4. 对三方评估清单的处置

| # | 结论 | 处置 |
|---:|---|---|
| 1 Outbox 中继 | **采纳** | 单机使用服务内小批轮询，`SKIP LOCKED`、Kafka 确认后标记、允许重复投递；不增设 Debezium/Kafka Connect。 |
| 2 MQTT 大版本边界 | **采纳** | 新增字段且可忽略为同主版本兼容；字段删除、重命名、单位/语义/鉴权/路由变化为新 MQTT 大版本和新 Topic；接入方必须通过兼容矩阵。 |
| 3 共享 Outbox Topic | **采纳** | 取消 `evco.platform.outbox.v1`；业务事件使用所属领域 Topic，各 schema 独立 Outbox，DLQ 亦按生产领域隔离。 |
| 4 MinIO RTO | **部分采纳** | 保持用户要求的本机 MinIO 主存储；为回单、发票、监管证据定义离机复制状态、RPO/RTO、恢复和只读取证流程。不默认把外部对象存储改为主写。 |
| 5 V2G 演进 | **采纳** | `evco_v2g`、独立状态机和事件契约不复用充电订单；合规/负载阈值触发再拆服务。 |
| 6 资金 Saga | **采纳并纠正表述** | 下游事务失败且未提交 offset 会自动重投，并非天然“静默丢失”；但长期失败必须进入重试/DLQ、超时告警和订单—资金对账，不能只依赖幂等。 |
| 7/21 MySQL 资源耦合 | **采纳** | 提高 MySQL 内存/CPU权重、汇总连接池预算、资金保留连接和优先级；外部适配已拆出。单实例仍是共享故障域，资金 p95/redo/IO 达线时优先迁独立 MySQL，不能用 schema 假装物理隔离。 |
| 8 Redis CAS | **采纳** | Lua CAS 与 ClickHouse 使用同一四元裁决键；同设备键 Kafka 分区和状态合并器串行处理。 |
| 9 ReplicatedMergeTree | **部分采纳** | 单节点 Keeper + 单副本没有 HA，却要占资源，当前不采用。未来迁移采用新表/新集群并行回填、分区校验、双读切换与旧表保留，而非直接在海量表上冒险修改引擎。Runbook 和停机窗口必须预先定义。 |
| 10 双模式一致性 | **采纳** | `deployment_mode` 只可初始化写入、数据库唯一事实；各服务启动读取为不可变值，健康端点暴露摘要并由巡检比对。任何服务端接口都再次强制模式，不信任网关。 |
| 11 EMQX 恢复预算 | **采纳** | 以真实 TLS、报文和上游数压测确定连接速率、认证并发、队列磁盘和优先级；订单/控制优先、遥测反压。不能预先声称固定 200/s 或 500/s。 |
| 12 platform 模块资源 | **采纳** | 保留交易/IAM 与营销/运营/V2G 的线程池、连接池和超时隔离；营销/运营后台任务可降级。第三方调用已移出该 JVM。 |
| 13 目录迁移措辞 | **采纳** | 当前仓库无业务源码时称为“目标工程新建/归位”，不虚称代码迁移；有外部遗留代码才单列重构计划。 |
| 14 空服务冲突 | **采纳** | 阶段 0 只建有健康检查、镜像、配置、迁移入口和契约检查的架构跑道；没有职责的路由/消费者不部署。 |
| 15 CI/CD 低估 | **采纳** | 阶段 0 明确最小 CI：构建、契约、镜像扫描、备份/配置校验、迁移、健康检查、发布审计；高级灰度/自动回退后置。指定负责人和工期后才开始业务阶段。 |
| 16 缺日志/追踪排障 | **采纳** | 强制 JSON 日志、`traceId`/业务键索引和一键诊断脚本；Tempo/Loki 不常驻，允许导出至外部平台或本机短期文件。 |
| 17 技能与 Runbook | **采纳** | 发布前校验服务 Runbook、备份可读和负责人矩阵；恢复演练结果进入上线门禁。人员“必须两人熟练”不宜写成 CI 可验证事实，改为项目治理审计。 |
| 18 测试全覆盖 | **采纳** | 阶段 0/1：单元、ArchUnit、Testcontainers 核心链路；阶段 2：IOT/支付契约；阶段 3：E2E/k6；阶段 4：故障注入和协议模拟器。 |
| 19 Flyway | **采纳** | 每个 schema 独立迁移目录和责任服务；跨 schema 仅逻辑引用，不建立物理外键。 |
| 20 MyBatis-Plus 边界 | **已覆盖，重申** | 基础配置允许受控 CRUD；订单、账本、结算、权限、命令和复杂查询只能使用显式自定义 SQL/状态机。 |
| 22 验收指标 | **采纳** | 每阶段定义业务、积压、恢复、正确性和性能量化 DoD；最终数值由真实报文压测确定。 |
| 23 Bucket 复制 | **采纳** | Bucket 版本化、对象类复制策略、复制延迟监控、离机目标可读校验及证据类对象 RPO/RTO 进入 Runbook。 |
| 24 Kafka 保留 | **采纳** | 72 小时只作恢复缓冲，永久分钟留存唯一依赖 ClickHouse 离机备份和上游重放窗口。 |
| 25 Compose 自动重启 | **采纳** | `restart` 只处理进程退出，不是 HA；主机、磁盘、机房故障仍按恢复流程处理。 |

## 5. 反对者仍保留的风险

1. 8 核 32 GB 可以作为万台以内的起步包，不能在未完成真实字段、最短上报周期、查询并发、订单量和故障注入压测前承诺万台 SLA；更不能把它延伸为十万桩部署规格。
2. 单机六个服务是“隔离和可演进”，不是主机高可用。若客户要求主机故障持续服务，首先需要多故障域的数据库、MQTT、Kafka、ClickHouse 和对象存储方案，而不是先加 Nacos/Kubernetes。
3. 一个 MySQL 实例内的十个 schema 仍共享 I/O、redo 与 buffer pool；schema 是所有权和迁移边界，不是物理资源隔离。资金指标出现争用时应优先独立数据库。
4. `integration-service` 统一的是**外部协议防腐层**，不是所有外部平台的一锅同步调用池。支付、监管、门禁等适配器必须有独立线程池、连接池、超时、熔断和重试预算，且不能相互拖垮。
