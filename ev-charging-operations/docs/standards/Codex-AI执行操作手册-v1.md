# Codex AI 执行操作手册

> 版本：v1.0<br>
> 状态：现行辅助执行手册<br>
> 更新：2026-08-14<br>
> 适用：`charge-ai` / 充电运营平台；供用户向 Codex 下达可审计、可连续执行的工作输入。<br>
> 定位：本手册把已批准的计划和治理规则转写为可直接使用的输入模板；**不替代**需求、架构、审批日志或模块验收证据。

## 1. 使用方式与优先级

每次新建 Codex 对话，先粘贴“会话启动输入”，再粘贴一个且仅一个“工作指令”。Codex 必须先读取现行事实，再决定是否执行；不得仅根据聊天摘要、历史印象或本手册推断项目状态。

规则冲突时按以下顺序执行：

`用户本次明确批准 → 变更与审批日志 → 12 周实施计划 → 架构/安全/数据基线 → 本手册 → 局部 README`

本项目采用单人主导、AI 辅助、模块严格串行交付：

`需求/验收确认 → 后端、迁移、契约 → API 自动化与人工验证 → 前端 → E2E、权限、异常 → 完成记录、文档同步、提交与审查`

因此，输入中出现“做完”“继续”“全做了”等表述，也不构成跳过门禁、缩小范围、开始后续模块或启用真实外部能力的授权。

## 2. 每次会话的必贴启动输入

将下面整段作为新会话的第一条项目输入。其后的方括号内容由用户按当次目标替换。

```text
你正在维护 /Users/cbl/Project/charge-ai 的充电运营平台。

先严格执行项目根目录 AGENTS.md 的会话恢复顺序：
1. 阅读 AGENTS.md。
2. 阅读 ev-charging-operations/docs/requirements/充电运营平台12周全功能交付实施计划-v3.md。
3. 阅读 delivery/execution/00-执行总控台账.md 与 01-模块路线图与依赖矩阵.md。
4. 若要改动，阅读 02-变更与审批日志.md；若要宣称完成，阅读 03-模块完成记录.md、04-一致性核对清单.md 与 05-SVN待同步清单.md。
5. 在任何修改前，运行 git status -sb、svn update、svn status，并检查本次涉及文件。

遵守：单一主实现者写入；模块严格串行；API 门禁未通过不得开始前端；不得修改已执行 Flyway；不得跨服务写 Schema；不得把 Mock 当作真实微信、监管或 V2G 门禁；不得索取、打印或保存任何凭据值。

先用简短中文报告：当前模块、该模块当前门禁、工作区/SVN 状态、拟执行的最小下一步。随后执行用户下面的工作指令；若需要用户审批、真实凭据、真实外部环境、范围变化、延期或周末加班，停止在安全边界并说明需要什么决定。
```

## 3. 当前阶段：W1 的首个可执行输入

当前计划中 W0 已验证，W1 “工程跑道”尚未开始，计划开始日为 2026-08-17。W1 的第一个工作不是创建业务页面或直接写业务代码，而是完成需求/验收与字段级契约评审，以及工程质量门禁。

在 2026-08-17 或获批准提前启动时，使用以下输入：

```text
开始 W1 工程跑道的“需求/验收确认与契约评审”阶段，不进入业务实现、前端页面或真实外部联调。

请在恢复项目状态后，按现役需求、架构基线、事件目录和高风险契约，产出并写入可审查的 W1 评审材料。范围必须至少覆盖：
- 个人用户主档、渠道身份映射及会话/隐私安全；
- 个人现金充值资金批次、支付路由快照、原路退款；
- 充电订单的场站结算方案快照、退款/补差调整、锁单或付款后不得回写；
- 独立 V2G 收益余额及提现关闭态；
- evco_ecosystem 的监管档案、任务、回执、漏推/补推与对账；
- 每个 Kafka Topic 的唯一发布者、消费者组、幂等键、重试与 DLQ 责任；
- DDL、OpenAPI、AsyncAPI/MQTT 的字段、版本和错误码边界。

先列出权威来源与评审清单；对每项给出事实归属、服务/Schema、版本策略、正常/幂等/越权/异常验证条件和待决项。只有用户确认评审结论或现役基线已覆盖所有待决项后，才开始 W1 的迁移、契约或 CI 实现。不要创建空 Topic、消费者、迁移、端点或前端页面。
```

## 4. 可直接使用的任务输入模板

### 4.1 需求/验收确认

```text
处理 [W数字/模块名称] 的需求与验收确认阶段，不写生产代码。

阅读该模块对应的需求基线、业务规则、架构边界、契约目录、执行台账和依赖矩阵。输出并写入一份可审查的验收清单，逐项包含：菜单/用户场景、前置条件、成功结果、失败/拒绝路径、数据归属、权限与数据范围、审计、幂等、补偿、外部依赖与关闭态、API/事件/迁移/前端/E2E 证据位置。

标出任何范围歧义、未批准外部能力或需要用户决定的事项。未获得所需批准前，不开始后续阶段。
```

### 4.2 后端、迁移与契约

```text
处理 [模块] 的后端、迁移与契约阶段。前提是该模块的需求/验收确认已经留有通过证据；先核对该证据，再执行。

实现范围限定为已批准的 DDL、后端业务模块、版本化 OpenAPI/AsyncAPI/MQTT 契约、错误码、审计、数据范围、Outbox/补偿与脱敏 Mock 夹具。所有新增资产遵循业务模块优先传统分层和中文注释规范；迁移只能前向新增，不能修改已执行 Flyway。

完成后运行单元、架构、迁移和契约测试；报告文件清单、迁移版本、契约版本、未解决风险与 API 门禁结果。API 自动化与人工验证未通过前，不创建任何前端功能。
```

### 4.3 API 自动化与人工验证

```text
处理 [模块] 的 API 门禁。不要开始前端。

基于已冻结的契约，为每个接口或事件补齐并运行自动化验证：正常路径、参数边界、幂等/重复回调、越权和数据范围、并发或状态冲突、外部失败/超时、补偿及审计。提供可重复的脱敏夹具和人工验证步骤、输入、预期结果、实际结果与证据路径。

若有任一必测项失败或契约不一致，修复仅限该后端/契约阶段，并保持前端未开始。全部通过后，明确记录“API 门禁通过”，再等待或执行前端任务。
```

### 4.4 前端实现

```text
处理 [应用/模块] 的前端阶段。先核对对应 API 门禁已通过并给出证据；若未通过，停止，不写页面。

仅使用已稳定的版本化 API 客户端，实现已批准菜单和场景。按 frontend/apps/<app>/ 与 modules/<module>/<feature>/ 组织，补齐准确中文注释、加载/空/错误/无权限/关闭态、移动端和桌面端适配、可访问性与脱敏展示。M1 的可用性必须按应用发布、渠道健康、业务开关、场站开放、用户资格判定，不能实现为 P1 对个人的页面/功能权限。

交付前运行前端测试、构建及必要截图检查，并列出进入 E2E 前还需要的接口、夹具或外部 Mock。
```

### 4.5 E2E、权限与异常验证

```text
处理 [模块] 的 E2E、权限与异常验证。该模块的 API 门禁和前端实现必须均已有通过证据；先核对。

覆盖用户主流程、重复请求/回调、越权和数据范围、异常提示、外部超时与失败、补偿/重试/DLQ、审计及适用的独立/IOT 协同模式。外部资料不足时只使用确定性 Mock 和脱敏夹具，并将真实渠道门禁保持为待完成。

输出可复跑命令、环境/夹具、用例结果、缺陷等级、截图或日志证据路径。任何 P0/P1 缺陷、权限越界、资金不一致或关键状态机错误都阻止模块完成。
```

### 4.6 模块完成、文档与双版本库留证

```text
为 [模块] 执行完成前核对与留证；不要把“代码完成”直接写成“模块完成”。

逐项核对需求/验收、迁移/契约、API 自动化与人工验证、前端、E2E/权限/异常、Runbook/API/用户文档、代码审查和已验收模块回归。更新 00 总控台账、03 模块完成记录、04 一致性核对清单及受影响文档。

修改前后检查 git/svn 状态、diff、敏感信息和适用测试。公司内网可用时，只提交本次已验证范围到 SVN，使用简洁中文说明并记录 revision；再创建聚焦的中文 Conventional Commit、推送分支并建立草稿 PR。若 SVN 因不在内网不可达，按 05 待同步清单登记范围、Git commit、验证和预定中文 SVN message；不得把模块或发布标为完全完成。
```

## 5. 高风险领域的补充输入

### 5.1 M1 登录、身份与隐私（W2）

```text
实现或验证 W2 的 M1 渠道身份链路。微信/支付宝只作为渠道，不得重复建立个人业务事实。

渠道授权成功后，以“渠道 + 应用实例 + 外部主体标识”唯一映射；仅用服务端验证、规范化后的手机号匹配既有个人用户。命中时幂等更新绑定和登录资料，未命中才创建用户主档。身份已绑定他人、手机号冲突/锁定或资料不完整时，拒绝自动合并，写入审计与人工处置事项。未授权手机号的访客只能浏览公开站点，不能交易、退款、核销、开票或使用 V2G。

不得在 M1 提供自助绑定、解绑或合并，不得信任客户端直接上传的手机号或授权码。真实微信配置缺失时只完成 C1-Mock，C1-W 必须保持待真实验证。
```

### 5.2 支付、钱包与租户结算（W6/W8）

```text
实现或验证资金相关模块时，优先保护资金事实可追溯性。

每笔现金充值必须有资金批次，保留原支付交易、渠道、应用实例、商户引用/路由版本、实收、已消费/冻结/退款与可退款余额；赠送金、红包、积分不能成为现金退款来源。退款必须回到原交易路由和资金批次。

商户变更只影响新交易；旧商户必须可供历史查询、原路退款和对账，直到可退款余额、在途退款和对账差异清零或有获批处置。租户结算只按充电订单的场站结算方案快照计算：未消费充值退款不进租户结算；订单退款、补差和价格修正生成调整；锁单或付款后只追加调整，绝不回写历史账单。

必须测试重复回调、混合新旧商户、部分消费、部分退款、退款失败和人工补偿；不能以 Mock 代替真实微信支付/原路退款生产门禁。
```

### 5.3 设备控制、监管与 V2G（W4/W10/W11）

```text
实现或验证设备控制、监管或 V2G 时，严格按高风险状态机与版本化 Schema 执行。

控制命令必须保留意图、权限、幂等、有效期、发送、上游 ACK、设备业务回执、超时/未知结果、重试/DLQ 和人工处置；ACK 不得当作设备已执行。监管由 ecosystem-service 在 W10 达到内部闭环，不能给监管方设备控制权；真实目标接入必须另以 C3-R 留证。

W11 仅允许 V2G 模拟会话、模拟计量和独立收益余额；真实放电控制、真实收益结算、提现申请/付款/回单/提现记录均保持关闭，除非用户以独立审批记录提供受控现场、设备/车辆/计量清单、停止回退和 E2E 范围。
```

## 6. Codex 必须停止并要求用户决定的情形

出现以下任一情形，Codex 应先报告事实、影响和可选方案，不得自行继续：

| 情形 | 必须请求的决定 |
| --- | --- |
| 需求新增、菜单范围变化、已验收模块修改 | 用户批准的变更记录，含兼容、回归和日期影响。 |
| 需要提前启动、周末开发、延期或缩减范围 | 用户批准的排期决定；不得自行调整 60 个工作日或 11/20 目标。 |
| 需要真实微信/支付/监管/设备/V2G 联调 | 用户在受控系统完成配置或提供可用环境；不得索取、粘贴或记录秘密值。 |
| 契约、数据归属、状态机或迁移规则存在冲突 | 用户或已授权的需求/架构结论；不得选一个“看起来合理”的版本实施。 |
| 发现 P0/P1 缺陷、资金不一致、越权、数据泄露或无法恢复的迁移风险 | 修复授权与回归范围；后续模块保持阻塞。 |
| SVN 认证、证书、权限、冲突或本地差异问题 | 先解决或报告；不得称为“外网待同步”。 |
| 用户要求删除、覆盖、重写历史或暴露凭据 | 明确目标和恢复方式；禁止破坏性命令、改写已执行迁移或输出秘密。 |

## 7. 每次交付的输出格式

要求 Codex 在完成一个小任务时使用以下结构，避免“看起来完成”却没有证据：

```text
结果：一句话说明已完成的可验证事实，或明确未完成原因。
范围：修改的文件/模块，以及明确未修改的高风险范围。
验证：执行的命令、测试结果和人工检查；失败项必须列出。
门禁：当前处于哪个模块阶段；是否允许进入下一阶段。
外部依赖：真实门禁、配置、环境或用户决定的待办。
版本库：Git/SVN 状态；若有 SVN 待同步，指向清单行。
下一步：唯一最小可执行动作。
```

## 8. 续接、审查与排障输入

### 8.1 续接上一会话

```text
继续充电运营平台工作，但不要信任此前聊天结论。按项目 AGENTS.md 完整恢复状态、读取当前台账与相关完成/审批记录、同步 SVN，并对照 Git/SVN diff 判断上次实际停在哪个门禁。只执行已批准模块的最小下一步；先报告恢复结论，再动手。
```

### 8.2 只读代码审查

```text
对 [分支/提交/文件范围] 做只读审查，不修改文件、不提交、不推送。先读取该模块的需求、契约、依赖矩阵和完成证据，再检查正确性、状态机、权限、幂等、事务/补偿、迁移兼容、敏感信息、测试缺口和与现役文档的一致性。按严重性列出可复现问题；没有问题时说明已检查范围和剩余风险。不要把风格偏好当作阻断问题。
```

### 8.3 故障诊断

```text
诊断 [现象]，默认只读：收集日志、配置元数据、测试结果、契约与代码路径，定位最可能的根因和证据链。不要修改生产代码、数据库或外部系统。给出最小修复建议、影响模块、回归范围和是否需要变更审批；只有我明确要求后再实施修复。
```

### 8.4 处理未完成的 SVN 同步

```text
我已回到公司内网。不要开始新开发：先读取 05-SVN待同步清单.md，执行 svn update，按待同步项从旧到新核对范围、Git commit、测试和敏感信息，再以每项最小范围提交 SVN 并回填实际 revision 与同步时间。认证、证书、权限或冲突失败时停止并报告，不得标为外网待同步。完成后检查 Git/SVN 工作树一致性。
```

## 9. 用户输入的简写规则

用户可用以下简写，Codex 仍必须应用本手册的恢复、门禁和停止规则：

| 简写 | 等效工作意图 |
| --- | --- |
| `开始 W1` | 使用第 3 节的 W1 首个输入，先做评审和质量门禁，不写业务功能。 |
| `继续` | 使用 8.1 恢复输入，只做当前门禁的最小下一步。 |
| `做 W2` | 仅在 W1 完成记录和解锁条件已通过后，开始 W2 的需求/验收确认。 |
| `修这个问题：[现象]` | 先按 8.3 诊断；用户明确要求修复时才修改。 |
| `审查这次改动` | 使用 8.2 只读审查。 |
| `准备提交` | 使用 4.6 的完成前核对与双版本库流程；不自动把未过门禁的模块标记完成。 |
