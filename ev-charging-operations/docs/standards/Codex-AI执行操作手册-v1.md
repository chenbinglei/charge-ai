# 充电运营平台分阶段执行与审核手册（Codex）

> 版本：v1.2<br>
> 状态：现行项目执行 SOP<br>
> 更新：2026-08-14<br>
> 适用：W1–W12、P1/P2/M1–M4/D1 的全部 106 个菜单/入口。<br>
> 用途：规定 Codex 每一步先交付什么、运行哪些验证、何时必须停下交由用户审核，以及获批后下一步做什么。

## 1. 使用规则

本手册采用**阶段审核制**，不是一次性自动做完整个项目：一个模块必须完成当前阶段的产物和验证，交由用户审核；用户确认“通过”后，Codex 才执行下一阶段。用户无需每次重述具体工作，只需给出审核结论：`通过`、`需要修改：…`、`拒绝/调整范围：…`。

每次会话开始，Codex 必须恢复项目事实：阅读 `AGENTS.md`、12 周计划、总控台账、依赖矩阵；改动前阅读审批日志，完成判断时阅读完成记录、核对清单和 SVN 待同步清单；随后执行 `git status -sb`、`svn update`、`svn status`。

当前计划：W1 从 2026-08-17 开始，W0 已验证但不等于 W1 开始。2026-09-25 至 2026-10-07 不开发。未经记录批准，不能提前启动、加班、延期、缩减范围、修改已验收模块或启用真实外部能力。

## 2. 每个模块必须执行的八个步骤

下表是 W1–W11 的固定流程。除非本手册的“例外模块”说明，否则不得跳过、合并或颠倒步骤。

| 步骤 | Codex 执行内容 | 必交付物 | 验证与停止点 | 用户下一句 |
| --- | --- | --- | --- | --- |
| 0. 会话恢复 | 恢复现行事实、同步 SVN、检查双版本库和当前门禁。 | 当前模块/阶段/风险/工作区状态简报。 | 发现冲突、未同步 SVN、未批准变更或排期问题时停止。 | `继续第 1 步`。 |
| 1. 需求与验收 | 将本模块菜单、规则、场景拆成可实施项；明确角色、主流程、异常、数据归属、权限、审计、外部依赖、验收条件和不做事项。**不写生产代码。** | `delivery/acceptance/Wx-模块需求与验收包.md`；逐项菜单覆盖矩阵与待决问题。 | 需求包完整且与现役基线一致后，停下等待审核。 | `需求通过，进入第 2 步`，或说明修改。 |
| 2. 契约、DDL 与技术设计 | 依据已通过需求，设计服务/Schema 所有权、前向迁移、状态机、OpenAPI/AsyncAPI/MQTT、错误码、幂等/补偿、测试数据与前后端边界。**不写业务 UI。** | `docs/design/` 设计说明；`contracts/` 草案；迁移/接口清单和 API 验收用例。 | 设计自检通过后，停下等待审核；涉及高风险资金、控制、监管、身份时此审核为必经。 | `设计通过，进入第 3 步`，或说明修改。 |
| 3. 后端与迁移 | 落地已审核的传统分层业务代码、Flyway、契约、Outbox/补偿、权限/数据范围、审计、脱敏 Mock 与单元/集成/契约测试。 | 可运行后端、前向迁移、版本化契约、自动化测试和开发说明。 | 构建、架构、迁移、单元、集成、契约测试通过；失败则在本步骤修复。 | 无需审核指令，Codex 自动进入第 4 步。 |
| 4. API 门禁 | 补齐 API 自动化与人工验证：成功、边界、幂等/重复回调、越权、状态冲突、超时、补偿、审计。 | API 测试报告、人工验证记录、接口示例、已知限制。 | 全部通过后停下；API 未过绝不开始前端。 | `API 通过，进入第 5 步`，或说明问题。 |
| 5. 前端 | 只调用通过 API 门禁的稳定接口；实现本模块 P1/P2/M1–M4/D1 页面及加载、空、错误、无权限、关闭/降级态、中文注释、可访问性和响应式。 | 前端页面/组件/测试、桌面与移动截图、接口映射。 | 构建、lint、前端测试、截图检查通过后停下。 | `前端通过，进入第 6 步`，或说明修改。 |
| 6. E2E 与验收 | 联调前后端、权限、异常、补偿、跨端/独立-IOT 模式与受控外部 Mock；修复属于本模块的缺陷并重复测试。 | E2E 报告、权限/异常报告、演示路径、缺陷清单。 | 主流程、幂等、越权、异常、补偿均通过后停下等待最终验收。 | `E2E 通过，进入第 7 步`，或说明问题。 |
| 7. 完成留证 | 更新台账、完成记录、核对清单、Runbook、API/用户文档；检查差异、敏感信息和回归；提交 SVN/Git、推送分支、更新草稿 PR。 | Git commit、SVN revision、完整模块完成证据。 | 仅在所有证据齐全时将模块标为已验收；随后报告下一模块的第 1 步。 | `开始下一模块第 1 步`。 |

### 阶段内的强制规则

- Step 1 未获用户审核通过，不得进入 Step 2；Step 2 未通过，不得写后端；Step 4 未通过，不得写前端；Step 6 未通过，不得宣称模块完成。
- Step 3、5、6 中发现缺陷，Codex 自行在同一步骤修复并复测；若修改超出已审核需求/设计，退回对应审核步骤。
- 每次审核交付均要给出：变更文件、验证命令与结果、未做范围、风险/待决项、下一步骤入口。不得只说“已完成”。
- 所有生产资产采用业务模块优先传统分层和中文注释；Flyway 只新增不改写；跨服务不直接写 Schema；前端不得绕过 API；真实凭据绝不进入聊天、代码、日志或文档。

## 4. 每个阶段的审核交付格式

Codex 交付审核时使用以下结构，使用户可以直接检查并回复结论。

### Step 1：需求与验收审核包

```text
模块：W? 名称
本次范围：菜单/入口/子页面清单
用户与角色：谁可以做什么、数据范围
主流程：从入口到成功结果
异常与拒绝：权限、状态、重复、外部失败、人工处置
业务规则：不可变约束、数据归属、审计、幂等、补偿
外部依赖：Mock、真实门禁、关闭态
验收清单：后端/API/前端/E2E 的可验证条件
不在本次范围：明确列出
待你确认：仅列出有决定价值的问题
```

### Step 2：契约与技术设计审核包

```text
服务与数据：服务、Schema、表/实体所有权及跨服务协作
迁移：新增 Flyway 清单、兼容/回填/回滚说明
接口与事件：OpenAPI/AsyncAPI/MQTT、请求响应、错误码、版本与幂等键
状态与补偿：状态机、超时/重试/DLQ、人工处置
安全：认证、授权、数据范围、审计、脱敏、保留/删除
测试：单元、集成、契约、API 人工验证的用例清单
前端边界：页面、状态、稳定 API 和关闭态
待你确认：只列真正影响业务或架构的选择
```

### Step 4：API 门禁审核包

```text
已交付接口/事件和版本：……
自动化结果：构建、迁移、单元、集成、契约、API 测试
人工验证：请求、预期、实际结果和证据位置
风险场景：幂等、越权、并发、异常、补偿、审计
未通过项：没有则明确“无”
前端可使用的稳定接口：……
```

### Step 5：前端审核包

```text
页面/入口：……
接口映射：页面调用的已通过 API
状态覆盖：加载、空、错误、无权限、关闭/降级
截图：桌面端、移动端及关键异常态
前端验证：构建、lint、单元/组件测试
待修项：没有则明确“无”
```

### Step 6：E2E 最终验收包

```text
主流程演示：……
异常/补偿/越权：……
跨端与外部依赖：Mock 或真实门禁状态
E2E 与回归结果：……
缺陷：按 P0/P1/P2 分类；P0/P1 必须为零
完成证据：迁移、契约、测试、截图、Runbook、文档
请求结论：允许完成留证 / 退回第 ? 步修改
```

## 5. 跨模块不可变规则

| 范围 | 必须持续通过的检查 |
| --- | --- |
| 个人身份 | 渠道映射幂等；冲突不自动合并；P1 不给 M1 个人配置页面/功能权限；未验证手机号不可交易。 |
| 支付与钱包 | 现金充值是可追溯资金批次；非现金权益不可现金退款；退款走原路由；旧商户保留历史义务。 |
| 结算 | 租户结算只按订单场站结算快照；未消费充值退款不进结算；锁单/付款后只追加调整。 |
| 企业 | 企业资金与租户隔离；车辆/电卡唯一有效分组；VIN/电卡/授信异常可处置。 |
| 设备与监管 | 控制有授权、幂等、有效期、回执和未知结果处理；监管没有设备控制权，真实接入须 C3-R。 |
| V2G | 首发只允许模拟与关闭态；收益独立；真实放电和提现均须另批。 |
| 数据安全 | 数据范围、审计、脱敏、留存、导出、短时链接和密钥引用可验证。 |

## 6. 哪些事不需要、哪些事必须需要你的审核

不需要用户逐项审核：本步骤内的编码细节、测试补齐、同一步骤内缺陷修复、格式整理、文档链接修复、双版本库的例行提交。

必须审核：所有 Step 1 需求包、所有 Step 2 高风险契约/数据设计、所有 Step 4 API 门禁、所有 Step 5 前端、所有 Step 6 E2E 最终验收；以及范围/排期/真实外部能力/上线等审批事项。这样既避免你为小事反复输入，又确保需求、接口、页面和最终结果都由你把关。

## 7. 当前第一步

当前位于 **W1、Step 1：需求与验收**。Codex 的第一份交付应是《W1 工程跑道需求与验收包》，内容包括 W1 的工程质量门禁和所有后续模块必须冻结的身份、资金、结算、V2G、监管、Kafka 契约范围。交付后停止，等待用户审核；用户通过后才进入 W1 Step 2。
