# 文档与代码输出归档规则

> 版本：v1.0
> 状态：现役规范
> 用途：约束所有需求、设计、代码、测试与交付资产的输出目录与归档去向。

## 1. 基本要求

后续需求、设计、代码、测试、部署和交付资产必须输出到 `ev-charging-operations/` 下对应目录；正式产物不存放在项目根目录、下载目录或临时目录。

## 2. 文档输出路径

| 产物 | 目录 |
|---|---|
| 需求来源、范围基线、菜单、角色权限、验收需求、版本计划 | `docs/requirements/` |
| 架构、领域边界、流程图、数据模型、状态机、技术决策 | `docs/design/` |
| 内部 API 契约、错误码、版本说明、联调记录 | `docs/api/` |
| IOT、支付、停车、门禁、闸机、监管、第三方设备资料 | `docs/integrations/` |
| 用户手册、培训资料、FAQ | `docs/user-guide/` |
| 编码、安全、日志、测试和文档规范 | `docs/standards/` |
| 发布、部署、验收资料 | `delivery/releases/`、`delivery/deployment/`、`delivery/acceptance/` |
| 现行执行总控、模块依赖、审批、完成证据与一致性检查 | `delivery/execution/` |
| 已替代、未采纳或退役的资料 | `archive/requirements/`、`archive/design/`、`archive/integrations/`、`archive/delivery/`、`archive/code/` 按分类归档 |

## 4. 约束

1. 正式文档使用 Markdown；流程图使用 Mermaid 源码随文档归档。
2. 文件使用中文业务主题命名，可加 `-v1`、`-v2`；不得使用“最终版”“临时”等无语义名称。
3. 需求、设计、集成文档开头应标明目的、范围、依赖、版本和状态。
4. 未确认结论必须标为“待确认”。
5. 不提交真实密码、证书、Token、商户密钥、IOT 地址/Topic 或生产连接串；仅记录脱敏示例和保管方式。
6. 新增或调整目录职责时，必须同步更新 `STRUCTURE.md`。
7. 已归档文件须移入 `archive/` 对应分类并在首部说明归档原因、归档日期与当前替代资料；归档文件不得继续出现在现役文档入口中。现行计划被替代时，保留其完整内容与 Git 历史，不得删除。
8. 所有新技术标识必须符合 [平台技术命名规范 v1](平台技术命名规范-v1.md)。
9. Git 仓库、分支、提交、凭据引用和泄露轮换必须遵循 [代码仓库与凭据管理规范 v1](代码仓库与凭据管理规范-v1.md)；任何 token、密码、私钥、证书或生产连接串均不得提交。
10. `delivery/execution/` 的五份治理记录分别是当前事实、依赖、审批、完成证据和一致性检查的唯一入口；记录修订须追加修订原因、时间和替代记录标识。
11. 后端、前端和测试的模块内目录、依赖方向、注释与质量门禁只以《[全栈研发工程规范](全栈研发工程规范-v1.md)》为准；本表只负责定位资产，不另行定义平行分层规则。
