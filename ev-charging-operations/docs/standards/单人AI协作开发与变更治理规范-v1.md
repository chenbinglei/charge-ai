# 单人 AI 协作开发与变更治理规范

> 版本：v1.4
> 状态：现行规范
> 生效日期：2026-08-13
> 适用范围：充电运营平台的需求、代码、配置、测试、交付与文档。

## 1. 目的与唯一事实来源

本规范保障单人主导、AI 辅助的模块化串行交付，防止多写入者冲突、已验收模块被静默改坏、配置/凭据泄露或跨对话丢失上下文。

| 事实 | 唯一权威位置 |
| --- | --- |
| 范围、日期、阶段、外部能力口径 | `docs/requirements/充电运营平台12周全功能交付实施计划-v3.md` |
| 当前模块、预测、阻塞、下一动作 | `delivery/execution/00-执行总控台账.md` |
| 前置、后置、解锁和回归范围 | `delivery/execution/01-模块路线图与依赖矩阵.md` |
| 新增、变更、延期、加班、批准与撤回 | `delivery/execution/02-变更与审批日志.md` |
| 模块代码、测试、验收与文档证据 | `delivery/execution/03-模块完成记录.md` |
| 每次完成或修改后的同步检查 | `delivery/execution/04-一致性核对清单.md` |

## 2. 角色与写入权限

- 主实现智能体是唯一可写生产代码、迁移、契约、测试、配置和项目文档的角色。
- 架构、测试、变更影响和安全审查智能体默认只读；可运行验证、审阅 diff 和提出测试清单，但不得直接改文件。
- 用户是唯一批准人，负责范围新增、冻结模块修改、延期、加班、条件渠道真实启用、上线与回滚决定。
- 主实现智能体不得把审查意见当作批准；批准必须在审批日志中有用户结论。

## 3. 模块门禁

模块顺序固定为：需求/验收确认 → 后端/迁移/契约 → API 自动化与人工验证 → 前端 → E2E/权限/异常 → 完成记录、文档同步、提交与审查。

1. 前端不得在 API 门禁通过前开工。
2. API 与 E2E 阶段均须测试；资金、订单、权限、设备控制、监管与 V2G 必测幂等、越权、异常、补偿和审计。
3. 每个模块提交前更新完成记录、Runbook、契约说明及受影响用户文档；通过审查后冻结。
4. 模块出口失败时停止进入下一模块，并提交给用户决定延期、加班或新增功能的处理。不得自行裁剪范围或压缩测试。

## 4. 变更、兼容与冻结

冻结模块的任何改动须先建审批记录，明确原因、影响、兼容性、新 API 版本或前向兼容迁移、数据回填、回归、排期影响和用户批准结论。

- 禁止改写已执行 Flyway 迁移；用新迁移完成兼容演进。
- 禁止破坏已验收 API；破坏性变化使用新版本并保留旧版本至受影响客户端完成迁移。
- 禁止跨服务直接写其他服务 Schema；跨服务事实通过契约、Outbox 和受控消费完成。
- 只要变更涉及用户流程、权限、Schema、外部适配器、部署或运行手册，就必须同步更新对应文档与完成证据。

## 5. 凭据与渠道配置

- AppID、Secret、商户号、证书、私钥、APIv3 密钥及第三方凭据只由专项授权管理员在 P1 受控页面或批准的 Secret Manager 维护；平台只展示脱敏引用、状态、版本和审计。
- M1 是渠道中立业务产品。微信是首个真实上线渠道；支付宝配置、身份/支付抽象和关闭态是当前范围，支付宝客户端发布或真实联调须走审批记录。
- M1 面向公众，P1 不管理个人用户的小程序页面或功能权限。应用生命周期、内容、已批准业务开关和灰度投放不构成角色/页面授权；登录、账户状态、支付/余额、实名或 V2G 授权等仅作为业务资格校验。
- W2 的渠道授权登录必须幂等创建或更新统一个人用户主档及渠道身份映射；W6 才交付依赖订单、资金和权益事实的 P1 个人用户 360°运营视图。不得因微信/支付宝渠道不同重复建立个人用户、钱包、订单或权益。
- C1/C2 等配置通知必须在总控台账和完成记录中留痕；不得通过聊天、Git、日志、Issue、PR 或导出传递凭据值。
- 未具备真实外部资料时，可用版本化渠道适配器、确定性 Mock 和脱敏夹具完成内部 API/E2E；Mock 与真实 C1/C2 必须分别记录。真实微信登录、支付、结果通知和原路退款仍是生产 Go 门禁，Mock 不得替代或标记其完成。
- 个人钱包现金充值必须按原支付交易、商户路由和可退款余额建立资金批次，非现金权益不得作为现金退款来源。商户迁移时新商户只承接新交易，旧商户保留历史查询、原路退款、对账和退款资金；未经用户批准不得提前关闭旧商户或改由新商户退款历史交易。
- 租户结算只依赖充电订单及场站结算方案快照，不依赖个人充值商户或资金批次。未消费充值退款不进入租户结算；订单退款、补差和后续修正必须产生结算调整，锁单或付款后仅可追加调整、追补或追收记录。
- V2G 首发只结算至独立用户 V2G 收益余额；提现申请、付款、回单和提现记录处于待定关闭态，任何启用均须以独立审批记录确认实名、风控、付款渠道、审计与回归范围。

## 6. 文档、提交与跨对话续接

- 新对话必须按根目录 `AGENTS.md` 的顺序读取现行计划和执行台账，不得只依据聊天摘要恢复工作。
- 每次台账修订追加修订原因、时间和替代记录标识；Git 历史保留前后事实。
- 每个模块完成时，执行一致性核对清单；需求、契约、代码、测试、部署/Runbook 与用户文档不得出现互相矛盾的现役说法。
- 提交遵循项目 Git 规范，聚焦单一目的；不暂存不相关文件，不推送未审查或含敏感信息的变更。
- 本项目同时使用 Git 和 SVN：每项完成并验证的功能、配置、测试或文档改动均须立即以最小范围提交 SVN；通过模块全部门禁后，再以聚焦的 Conventional Commit 提交 Git。交付证据记录 Git commit 与对应 SVN revision。
- 提交前检查两套工作树的状态与 diff；`.git/`、`.svn/`、凭据、环境文件和构建产物不得跨版本库提交。发生错误时使用新的 Git revert 或 SVN 反向提交恢复，保留可审计历史，不重写或强制覆盖远端历史。
