# 充电运营平台技术命名规范

> 版本：v1.0  
> 状态：强制规范；适用于新建服务、数据库、表、字段、接口、事件、Topic、对象存储、配置、代码与部署资产。  
> 命名空间：`evco`，即 **EV Charging Operations**。这是本产品的技术命名空间，不是对外品牌、法人名称或域名；若产品正式英文品牌确定，可通过受控 ADR 一次性替换，禁止各模块自行创造缩写。

## 1. 原则与统一词汇

不存在一项覆盖服务、SQL、Java、MQTT、Kafka、S3 的“单一国际标准”。本规范采用跨语言、跨云和主流中间件通用的可移植约定：**ASCII 小写、明确命名空间、稳定业务语义、格式按载体区分、禁止无定义缩写**。

| 业务概念 | 唯一英文术语 | 禁止混用 |
|---|---|---|
| 充电设备（桩） | `charger` | `pile`、`station_device`、`charging_pile` |
| 枪口 | `connector` | `gun`、`port`（除物理网络端口） |
| 场站 | `station` | `site`（除地理站点以外不混用） |
| 租户 | `tenant` | `merchant`、`operator`（后二者是业务角色） |
| 个人充电客户 | `consumer` | `user`（`user` 仅用于通用身份） |
| 企业客户 | `enterprise_customer` | `company_user` |
| 充电订单 | `charging_order` | `order`、`charge_order` |
| 充电会话 | `charging_session` | `session`（通用登录会话需明确 `login_session`） |
| 设备指令 | `device_command` | `control_order` |
| 遥测 | `telemetry` | `telemetric_data` |
| IOT 协同模式 | `iot_collaborative` | `iot_mode`（仅 UI 展示文案可简写） |

保留的标准缩写只有：`api`、`iam`、`iot`、`mqtt`、`v2g`、`vin`、`id`、`url`、`tls`、`s3`、`dlq`。新缩写必须先加入本表并通过架构评审。

## 2. 服务、工程、镜像与部署

| 载体 | 格式 | 示例 | 规则 |
|---|---|---|---|
| 服务逻辑 ID、目录、Docker Compose service | `lower-kebab-case` | `api-gateway`、`platform-service`、`finance-service`、`device-connectivity-service`、`integration-service`、`telemetry-service` | 当前 6 个部署单元是唯一允许的新服务名。 |
| 容器/镜像仓库名 | `evco/<service>:<version>` | `registry.example.com/evco/platform-service:1.0.0` | 不使用 `latest`；镜像部署以 digest 固定。 |
| Kubernetes namespace（未来） | `evco-<environment>` | `evco-production` | 环境为 `development`、`test`、`staging`、`production`，禁止 `prod`/`dev` 混用。 |
| Java Maven artifactId | `evco-<service>` | `evco-finance-service` | groupId 使用公司受控反向域名，例如 `com.example.evco`；不得使用个人域名或未注册域名。 |
| Java 包 | `lowercase.dot.separated` | `com.example.evco.finance` | 类名 PascalCase，方法/变量 lowerCamelCase，常量 UPPER_SNAKE_CASE。 |
| 环境变量 | `EVCO_<SERVICE>_<NAME>` | `EVCO_FINANCE_DB_URL` | 只用大写 ASCII 与下划线；密钥变量不写入仓库。 |

`platform-service` 内部模块固定为 `iam`、`master`、`customer`、`trade`、`marketing`、`operations`、`v2g`；其中 `operations` 包含告警、工单、远程控制审计、应用发布、内容与通知，不另建“miniapp service”。`integration-service` 独占 `integration`（含监管适配）模块，`device-connectivity-service` 独占 `device-connectivity` 模块。模块包示例为 `com.example.evco.platform.domain.trade`。模块名不能在 SQL、Topic 和 API 中另造同义词。

## 3. 数据库、表、字段与 SQL 对象

### 3.1 物理数据库与 schema

MySQL 实例名为 `evco-mysql`；MySQL schema 使用 `evco_<domain>`：

`evco_iam`、`evco_master`、`evco_customer`、`evco_trade`、`evco_finance`、`evco_marketing`、`evco_operations`、`evco_integration`、`evco_device_connectivity`、`evco_v2g`。

ClickHouse 数据库为 `evco_telemetry`。数据库、schema、表、列、索引、约束、视图和 SQL 文件只能使用小写 ASCII `snake_case`，最大 63 个字符；不得使用 MySQL/ClickHouse 保留字、拼音、中文、空格、连字符或无语义序号。

### 3.2 表与字段

- 表采用**单数名词**：`tenant`、`charger`、`charging_order`、`ledger_entry`；关系表按语义使用 `iam_user_role`，不使用 `user_role_rel`、`t_user_role`。
- 表已由 schema 提供领域命名空间时不重复前缀：`evco_trade.charging_order` 合法；`evco_trade.trade_charging_order` 禁止。
- 主键统一为 `id`（`BIGINT UNSIGNED`，应用生成时序型全局 ID）；业务公开标识使用明确列，如 `order_no`、`device_code`、`external_id`，不得把业务编号作为所有表主键。
- 外键/关联列为 `<referenced_entity>_id`，如 `tenant_id`、`charging_order_id`；外部来源标识为 `<source>_external_id` 或统一的 `external_id` + `source_system` 联合唯一键。
- 时间统一 UTC：`created_at`、`updated_at`、`deleted_at`、`occurred_at`、`received_at`、`expires_at`；数据库列使用 `DATETIME(3)`，API 传 RFC 3339 UTC 时间戳。业务日/时区另存 `business_date`、`timezone`，不以服务器时区推断。
- 审计列使用 `created_by`、`updated_by`、`deleted_by`；状态使用 `<entity>_status` 或语义明确的 `status`，禁止 `flag1`、`type1`、`reserved_*`。
- Boolean 使用 `is_`/`has_`/`can_` 前缀，列类型 `TINYINT(1)`；金额使用 `<meaning>_amount_minor` 的 `BIGINT`，电量使用 `<meaning>_wh`，功率使用 `<meaning>_w`，禁止浮点参与账务或计量事实。
- JSON 仅用于受控扩展字段，命名 `extension_json`；可查询/结算/权限字段必须是显式列。

### 3.3 索引、约束、视图与迁移

| 对象 | 格式 | 示例 |
|---|---|---|
| 主键 | `pk_<table>` | `pk_charging_order` |
| 唯一约束/索引 | `uk_<table>__<columns>` | `uk_iam_user__tenant_id_username` |
| 普通索引 | `idx_<table>__<columns>` | `idx_charging_order__tenant_id_created_at` |
| 外键（仅确需数据库强约束时） | `fk_<child>__<parent>` | `fk_charging_session__charging_order` |
| ClickHouse 物化视图 | `mv_<source>__<target>` | `mv_device_connector_telemetry_1m__station_power_1m` |
| Flyway | `VyyyyMMddHHmm__lower_snake_case_description.sql` | `V202608120001__create_iam_user.sql` |

迁移文件放在拥有 schema 的目录，按 schema 独立版本序列。SQL 禁止 `SELECT *`、无条件更新/删除及跨 schema 直接写入；关键 SQL 显式列名、租户范围、状态/版本及受影响行数校验。

## 4. API、事件、Kafka、MQTT、Redis 与对象存储

| 载体 | 格式与例子 | 强制规则 |
|---|---|---|
| REST 路径 | `/api/v1/charging-orders/{chargingOrderId}` | 小写 kebab-case 复数资源名；路径版本只表示破坏性 API 大版本；动作使用子资源，如 `/commands`，不使用 `/startCharging`。 |
| JSON/OpenAPI 字段 | `lowerCamelCase`：`eventId`、`deviceCode`、`occurredAt`、`schemaVersion` | API/MQTT/Kafka payload 一律 lowerCamelCase；SQL 映射在 DTO/Mapper 明确转换，不混入 snake_case JSON。 |
| 事件类型 | `<domain>.<entity>.<past-tense>.v1` | `trade.charging-order.created.v1`、`finance.fund-hold.released.v1`；事件类型不得随内部类名改变。 |
| Kafka Topic | `evco.<domain>.<stream>.v1` | `evco.device.telemetry.ingress.v1`、`evco.device.control.command.v1`、`evco.finance.hold-request.v1`、`evco.integration.payment-result.v1`、`evco.device.telemetry.dlq.v1`。无通配符 Topic 名；Topic 大版本与 payload `schemaVersion` 对应的协议大版本一致。 |
| MQTT Topic | `evco/v1/{sourceCode}/{deviceCode}/{direction}/{messageType}` | 如 `evco/v1/iot-core/CHG001/up/telemetry`、`evco/v1/iot-core/CHG001/down/command`、`evco/v1/iot-core/CHG001/up/command-reply`。`sourceCode`、`deviceCode` 必须 ASCII URL-safe，且由 ACL 绑定；Topic 的 `v1` 仅代表 MQTT 契约大版本，payload `schemaVersion` 管理兼容演进。 |
| Redis Key | `evco:{environment}:{domain}:{entity}:{id}` | `evco:production:telemetry:connector:12345`；不在 key 放敏感信息或未转义用户输入。 |
| MinIO Bucket | `evco-<environment>-<purpose>` | `evco-production-attachment`、`evco-production-firmware`、`evco-production-raw-protocol`、`evco-production-export`、`evco-production-regulatory-archive`、`evco-production-backup`；小写、连字符、3–63 字符。 |
| MinIO Object Key | `<domain>/<yyyy>/<MM>/<entity-id>/<uuidv7>-<safe-file-name>` | `invoice/2026/08/98765/018f...-invoice.pdf`；原文件名不作为唯一键。 |

Kafka Topic、MQTT Topic、Bucket 和 API 均必须在 `contracts/` 中登记；生产创建权限只交由部署自动化账号，业务服务不得运行时任意创建 Topic/Bucket。

## 5. 禁止与检查

禁止：`common`、`util`、`manager`、`data`、`temp`、`test` 作为服务/schema/表/Topic 的业务名；`tbl_`、`t_`、`tb_` 前缀；环境缩写混用；中文/拼音/大小写混用；将密码、手机号、证件号、VIN、车牌或支付订单号放进 Topic、Redis key、Bucket 名或文件路径。

阶段 0 CI 必须实现以下检查：

1. Flyway 文件名、SQL object、Kafka/MQTT/MinIO 清单符合本规范；
2. OpenAPI JSON 字段为 lowerCamelCase，SQL 列为 snake_case；
3. 新服务目录和 Maven artifactId 只能来自已登记服务清单；
4. ArchUnit 验证 Java package 与 `platform-service` 模块不得反向依赖；
5. 迁移脚本和契约的命名审查是 Pull Request 必选项。

存量设计文档中的 `charging_*` schema、`charging_telemetry`、`charge.*`、`platform.*` Topic 视为设计阶段的旧命名；在尚未落库、未发布协议的当前窗口统一改为本规范的 `evco_*`/`evco.*`。一旦客户实例已有数据或外部上游已接入，任何改名必须走版本化迁移和兼容窗口，不得直接改生产对象。
