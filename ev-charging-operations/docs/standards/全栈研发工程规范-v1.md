# 充电运营平台全栈研发工程规范

> 版本：v1.11
> 状态：现役强制规范；全栈默认采用业务域包直挂的传统分层。
> 适用：本项目的 Java 21 / Spring Boot / MyBatis-Plus、Vue 3、uni-app、MySQL、ClickHouse、Kafka、MQTT、运维和交付资产。
> 依据：DEC-20260814-019、DEC-20260814-020、DEC-20260814-021、DEC-20260814-022；以《[平台技术命名规范](平台技术命名规范-v1.md)》和现行实施计划为上位约束。

## 1. 使用方式与底线

本文件定义本项目的全栈默认实现方式：**业务模块优先的传统分层**。它从 W1 起是后端、前端、测试、契约、数据库和运维资产的强制结构；W0 已取消的空包冻结不恢复，也不追溯要求 W0 创建业务包。每个需求在编码前先确定：需求编号、服务与业务模块、OpenAPI/事件/MQTT 契约、数据拥有者、迁移、测试层级和前端入口；任何一项未确定，不得先写页面或业务代码。

- 注释、日志说明、异常信息、测试显示名称、提交说明和文档**必须使用中文优先**；协议原文、标准术语、类名、字段名、第三方 SDK 固有文本可保留英文。所有新增类、接口、枚举、方法、字段、请求/响应模型、实体字段、关键代码块和测试用例均须有准确的中文说明；仅语义显然的局部变量、导入和单行赋值可免于重复注释。
- 本规范对代码注释的要求优先于一般文档的“避免逐行注释”原则：必须写的是对外模型、状态、字段、方法和风险代码块的业务说明；禁止的是只把语法逐行翻译成中文的噪声注释。自动检查只验证“应有说明的位置未缺失”，准确性、脱敏和业务边界仍由评审门禁判断。
- 不允许为了凑目录而创建空 Controller、虚假 Entity、空 Mapper、空 API、空 Topic 或空迁移。
- 新业务按“契约和迁移 → 后端与 API 验证 → 前端 → E2E”串行推进；不得绕过现行模块门禁。

## 2. 项目目录与职责

```text
ev-charging-operations/
├── backend/
│   ├── services/                  # 七个可部署服务，服务间不直接 Maven 依赖
│   └── libraries/                 # shared-kernel、contracts、starter、testkit
├── frontend/
│   ├── apps/                      # P1、P2、M1-M4、D1 七端
│   └── packages/                  # ui、design-tokens、types、api-client
├── contracts/                     # openapi、events、mqtt 的唯一事实来源
├── database/                      # 按拥有服务/schema 的 Flyway 与 ClickHouse 资产
├── tests/                         # 跨服务 unit、integration、contract、e2e、security、performance
├── platform/                      # 部署、可观测性、环境模板和 Runbook 对应资产
├── docs/                          # 需求、设计、规范、接口、集成资料
└── delivery/                      # 验收、执行证据、发布与部署记录
```

业务代码不得放进 `shared-kernel`；它只容纳无业务归属的错误模型、上下文、ID、时钟和幂等基础能力。`backend/libraries/starter/`（Maven artifactId `evco-starter`，包名 `com.elink.evco.web.*`）承载跨服务的 web 通用能力，分两层：基础层（链路追踪、全局异常、MyBatis 通用拦截器）对所有服务可用；管理端层（Bearer 鉴权、两档权限拦截）由配置开关 `evco.web.security.enabled` 控制，默认开启，个人小程序等无页面权限的服务置 `false` 后不装配任何权限组件。共享能力的归属判定：与 web/框架耦合的通用组件进 `starter`；无业务归属的领域基础（ID、错误模型、时钟、幂等）进 `shared-kernel`；仅本服务复用的技术辅助留在服务内根包 `config` 或域包 `util`，服务内不再新建 `common` 包。共享前端包不得保存页面业务状态或绕过服务端权限。任何跨服务事实都通过版本化契约协作，禁止跨 Schema 写入。

## 3. 后端服务目录：业务域包直挂的传统分层

每个服务以 `com.elink.evco.<service>` 为根包；启动类放根包，保证组件扫描覆盖全服务。业务域包直接挂在根包下（如 `platform/iam/`），不设 `module/` 中间层；域内采用传统层次，避免全服务的 `controller.trade`、`controller.iam` 等横向大包。**服务只含单一业务域时不设域包**，各层直挂根包（服务名即域）；多域服务各域包同级直挂。无自有持久化数据的网关不创建 `mapper` 或 `entity` 包。web 通用能力（鉴权、全局异常、链路追踪）归共享库 `starter`，服务内不再建 `common`/`support` 包。

```text
src/main/java/com/elink/evco/<service>/
├── <Service>Application.java       # 唯一启动类；不放业务逻辑
├── config/                         # Spring、持久化、OpenAPI 等全服务技术配置
├── <domain>/                       # 业务域包直挂（如 iam）；单域服务可省略此层
│   ├── controller/                 # HTTP/WebSocket 入站适配
│   ├── dto/                        # 请求、命令、分页条件等入参传输对象
│   ├── vo/                         # 面向调用方的响应对象；不得直接返回 Entity
│   ├── entity/                     # 持久化实体；一表一 Entity，不承担接口返回模型
│   ├── mapper/                     # MyBatis-Plus Mapper 和受控 SQL；仅访问本服务 Schema
│   ├── service/                    # 用例接口、事务语义和业务编排
│   │   └── impl/                   # Service 的唯一实现位置
│   ├── cache/                      # Redis 键规则与缓存访问封装
│   ├── util/                       # 域内纯技术工具（脱敏、指纹、格式化）
│   ├── convert/                    # Entity、DTO、VO 的显式转换器（按需）
│   ├── client/                     # 外部/其他服务的本地适配端口（按需）
│   ├── listener/                   # 已批准事件或消息的入站监听（按需）
│   ├── job/                        # 已批准的定时任务（按需）
│   └── exception/                  # 域业务异常与稳定错误码（按需）
```

高风险模块（资金、订单、设备控制、监管）在规模化后在对应 `service` 下按需追加 `policy/`、`calculator/`、`statemachine/`、`validator/` 子包；当前规模未达拆分阈值时不得预建空包。

### 3.1 包职责与禁止依赖

| 包 | 可以做什么 | 禁止做什么 |
| --- | --- | --- |
| `controller` | 参数校验、认证主体获取、调用 Service、DTO/VO 映射、HTTP 状态码。 | 调 Mapper、写事务、写 SQL、实现业务规则、返回 Entity。 |
| `service` / `impl` | 用例编排、权限/数据范围、幂等、事务、状态迁移、调用 Mapper/Client。 | 依赖 Controller、Servlet、VO、其他服务实现。 |
| `mapper` | 单服务 Schema 的读写、分页与锁定 SQL。 | 业务判断、跨 Schema 写、拼接用户输入、`SELECT *`。 |
| `entity` | 表字段、审计字段、持久化映射。 | 接收 HTTP 请求、作为事件或 API 响应、携带 Controller 注解。 |
| `dto` | 入参和服务命令的数据表达。 | 持久化注解、敏感字段默认回显、业务计算。 |
| `vo` | 稳定且脱敏的响应模型。 | 写库、被 Mapper 返回、暴露内部审计/密钥/完整敏感信息。 |
| `convert` | 显式完成 Entity/DTO/VO 转换。 | 偷偷填充业务状态、绕过 Service 校验。 |
| `cache` | Redis 键规则集中定义、TTL 与缓存访问封装。 | 散落 Redis 直连、在缓存层做业务判断、绕过 Service 校验。 |
| `util` | 域内纯技术工具（脱敏、指纹、格式化）。 | 承载业务规则；跨域/跨服务复用（应上移 starter 或 shared-kernel）。 |
| `config` / `exception` | 技术配置、统一错误外观、拦截器。 | 放业务用例或业务规则。 |

允许方向是 `<domain>.controller → service → mapper/entity`，`controller → dto/vo`，`service → dto/entity/mapper/client`。Mapper 只依赖 Entity 和技术框架；VO 不进入 Service/Mapper。不同域不得直接引用对方 Mapper 或 Entity；确有协作时通过本服务 Service 或明确的 Client/事件契约。架构测试至少阻止 Controller 直连 Mapper/Entity、Service 依赖 Controller/VO、Mapper 依赖 Controller/Service/DTO/VO，以及跨域 Mapper/Entity 依赖。

### 3.2 类、文件和命名

| 类型 | 固定格式 | 示例 |
| --- | --- | --- |
| Controller | `<资源>Controller` | `ChargingOrderController` |
| Service | `<资源>Service` / `<资源>ServiceImpl` | `ChargingOrderService` |
| Mapper | `<资源>Mapper` | `ChargingOrderMapper` |
| 持久化实体 | `<资源>Entity` | `ChargingOrderEntity` |
| 请求 DTO | `<动作><资源>Request` | `CreateChargingOrderRequest` |
| 服务 DTO | `<动作><资源>DTO` | `CreateChargingOrderDTO` |
| 响应 VO | `<资源>VO` / `<资源>DetailVO` | `ChargingOrderDetailVO` |
| 转换器 | `<资源>Convert` | `ChargingOrderConvert` |
| 异常 | `<资源>Exception` | `ChargingOrderException` |

一个 Java 文件只放一个顶级 `public` 类型。类名、方法、变量用英文技术名；数据库/API 字段遵循《平台技术命名规范》。布尔方法用 `is/has/can`，查询用 `get/list/page`，创建用 `create`，状态变更用准确动作如 `cancel`、`confirm`，不得滥用 `handle`、`process`、`data`、`util`、`common`。

### 3.3 编码模板

以下是未来有契约和迁移后才可使用的形态，不是 W0 业务代码：

```java
/**
 * 创建充电订单入口。
 *
 * <p>订单金额、用户资格和幂等判断由服务层完成；控制器不直接访问数据库。</p>
 */
@RestController
@RequestMapping("/api/v1/charging-orders")
class ChargingOrderController {
    private final ChargingOrderService chargingOrderService;

    @PostMapping
    ChargingOrderVO create(@Valid @RequestBody CreateChargingOrderRequest request) {
        return chargingOrderService.create(ChargingOrderConvert.toDTO(request));
    }
}

public interface ChargingOrderService {
    ChargingOrderVO create(CreateChargingOrderDTO command);
}

@Service
class ChargingOrderServiceImpl implements ChargingOrderService {
    /**
     * 在同一幂等键下只创建一个订单；事务边界覆盖订单与 Outbox 事实，不能只靠前端防重。
     */
    @Transactional
    public ChargingOrderVO create(CreateChargingOrderDTO command) { /* 省略业务实现 */ }
}
```

`@Transactional` 只允许在 Service 实现的公开用例方法上声明；异常必须包含稳定错误码、用户可读中文提示和可审计关联 ID。日志采用结构化字段并携带 `traceId`，绝不记录凭据、完整手机号、证件、支付数据或原始敏感报文。

## 4. 注释、格式与代码质量

- 类、接口、枚举、公共方法、字段、请求 DTO、响应 VO、Entity 与每个字段都必须写中文 Javadoc 或等效中文注释，说明业务含义、输入输出、必填/范围、脱敏、持久化或失败语义；状态机、资金/计量计算、权限/数据范围、事务/幂等、补偿、外部适配器必须同时说明不变量与风险边界。
- 复杂条件、循环、并发控制、异常转换、SQL、缓存键、前端分支和测试夹具必须在代码块前说明中文意图；禁止为逐行语法翻译添加噪声注释。
- TODO 格式固定为 `TODO(责任人/需求编号): 原因和截止条件`；没有需求编号或处置时间的 TODO 不得合入。
- 禁止 `@SuppressWarnings`、空 `catch`、魔法数、无边界分页、宽泛 `Exception`、`System.out`、裸字符串错误码和复制粘贴转换逻辑；例外须在评审记录说明。
- Java 使用 4 空格、UTF-8、LF、单行不超过 120 字符；前端使用 2 空格。提交前执行格式化、静态分析、单元测试和 `git diff --check`。
- 新增依赖必须说明用途、许可证、漏洞和替代方案；不得为了一个小功能引入大型框架。

## 5. 前端目录、UI 与调用边界

P1/P2/D1 采用 Vue 3；M1-M4 采用 uni-app。页面只属于各自 App；跨端复用设计令牌、无业务 UI 和 API 类型，不复制业务规则。

```text
frontend/apps/<app>/src/
├── app/                           # App 启动、路由/页面注册、全局布局和端内配置
├── modules/
│   └── iam/user/                  # 业务模块/功能；不得把业务代码分散到 src 根技术目录
│       ├── api/                   # 仅调用生成的 API Client
│       ├── components/            # 仅本功能复用的展示与交互组件
│       ├── composables/ constants/ stores/ types/
│       ├── views/                 # Web 页面，或由小程序薄页面入口引用的业务视图
│       └── __tests__/             # 单元和组件测试
├── shared/                        # 无业务归属的组件、组合式函数、工具、类型和样式
├── static/ styles/
└── App.vue main.ts                # 小程序另有 pages.json、manifest.json；pages/ 仅保留薄入口

frontend/packages/
├── api-client/                    # 由 OpenAPI 生成或受控封装
├── design-tokens/                 # 颜色、字型、间距、圆角、阴影、断点
├── types/                         # 契约共享类型，不能重复定义后端事实
└── ui/                            # 无业务归属的可访问组件
```

- `app/` 只负责启动、路由/页面注册、全局布局和端内配置；Web 路由直接指向 `modules/<module>/<feature>/views/`，小程序 `pages/<module>/<feature>/index.vue` 只负责框架页面注册并引用同模块视图。业务代码不得新建根级 `api/`、`views/`、`stores/` 或 `common/` 大包；历史资料中的 `frontend/common` 不是现役路径。
- `views/pages` 只负责页面组合；`components` 不直接调用 API；`api` 只调用生成客户端；`stores` 不保存密钥或替代服务端权限。跨端复用仅进入 `frontend/packages/` 或 `shared/`，且不得携带某一端的页面、租户规则或业务状态。
- Vue/TypeScript 的组件、props、emits、接口字段、组合式函数、store、接口封装、关键模板分支和异常处理均须有中文注释；页面注释说明业务入口、权限/数据范围和状态边界。
- 文件采用 kebab-case，Vue 组件使用 PascalCase；组件名、props、事件、状态、接口均有明确业务名。
- 每页必须实现 loading、empty、error、无权限、关闭态和网络降级；实时页面显示最后更新时间与重连状态。
- 视觉值只来自 `design-tokens`，不在页面散落颜色/间距魔法数；交互需具备键盘可达、焦点、标签和足够对比度。
- API 先经 OpenAPI 契约冻结，再生成客户端；不得手写重复接口、直接访问数据库、把权限判断只放在前端。

### 5.1 视口、分辨率与自适应基线

本小节是视口/分辨率/自适应的唯一现役权威；W1 起始值（源自《W1-工程跑道最终决策表》D-17 与 W1 验收包 §5.1）迁入此处，并经 DEC-20260820-008 按 2026-07 市场数据修订（断点五档改四档受控流式、验证视口八组、基础库 3.0.0）；后续修订只改本文件、W1 资料随丙类归档。

**Web（P1/P2/D1）视口与断点：**

- 策略依据（DEC-20260820-009，2026-08 市场实践调研）：P1/P2 采用受控流式——与 Ant Design 官方中后台适配方案（侧栏固定＋工作区动态缩放）及主流管理台实践一致；整体等比缩放（transform scale / rem 全局）经评估**否决**，仅限 D1 大屏等固定分辨率展示场景使用（等比在管理端存在小屏文字不可读、1px 边框缝隙、文字模糊、图表坐标偏移四项硬伤）。

- 主验收视口 1920×1080；验证视口八组：1920×1080、2560×1440、1536×864、1440×900、1366×768、1024×768、768×1024、390×844（覆盖 2K 高分屏、1080p@125% 缩放上报值 1536、老笔记本 1366 与主流移动端）。
- 断点重排（四档）：`>=1440` 受控流式桌面；`992–1439` 保持侧栏展开并压缩列宽；`768–991` 侧栏折叠为 64px、表格横向滚动；`<768` 表格转卡片列表、双列转单列、操作区换行。
- 受控流式规则（`>=1440` 档，1920/2560/4K 同样适用）：内容区跟随视口全宽、不设全局最大宽度；语义容器局部封顶——表单与详情描述容器 max-width 1200px、长文本/帮助/审计日志块 max-width 1000px（行长可读性）；表格全宽且列宽 token 化（固定列固定、弹性列 min-width 120px / max-width 360px）；仪表盘/统计卡片使用 `grid auto-fill minmax(360px, 1fr)`，宽屏多列重排而非拉宽卡片；行内操作列优先、工具栏吸顶以缓解宽屏操作动线。
- 排版 Token 起始值：H1 20/28、H2 16/24、正文 14/22、辅助 12/18；顶栏 64px、侧栏 210px/折叠 64px、工具栏 40px、表格行 48px/紧凑 40px；触控目标不小于 44px；间距为 8px 倍数、24 列栅格；数字/金额等宽字体。
- 内容安全：标题单行省略、地址两行省略、数值不换行；任意视口不得横向溢出、遮挡、重叠或出现不可访问操作。
- 系统缩放（DPI 100%/125%/150%）与浏览器缩放（80%–150%）下布局保持可用：不得出现双滚动条错位、固定定位元素漂移或点击目标偏移；缩放验证随八组视口截图一并留证。

**浏览器兼容矩阵（P1/P2/D1）：**

- 最低支持：Chrome ≥100、Edge ≥100、Firefox ≥100、Safari ≥15（ES2020＋、CSS Grid/Flex/`clamp` 全量可用为目标）。
- 国产 Chromium 系浏览器（360 安全浏览器极速模式、QQ 浏览器，国内桌面合计约 14% 份额）随「Chromium 内核 ≥100」一并支持；其 IE 兼容模式（Trident 内核）不支持，检测到时给出升级浏览器提示。
- 不要求支持 IE 任何版本；不引入为此妥协的 polyfill 负担。
- 新增依赖若抬高最低版本要求，须在评审中登记理由与影响面，同步更新本矩阵。

**小程序（M1-M4，uni-app）适配：**

- 尺寸单位使用 rpx（750rpx = 设计稿宽），仅边框 `1px` 与个别全局固定值用 px；不混用百分比与 rpx 表达同一布局意图。
- 安全区适配：顶部导航栏与底部 TabBar/操作区必须避让刘海屏、灵动岛与底部横条（`safe-area-inset-top/bottom`）；关键操作不得落入安全区外。
- 微信基础库最低版本 3.0.0（官方分布 2026-08：3.x 合计覆盖率 ≈99%，2.x 全系 <1%；低于设置值用户将收到升级提示）；开发调试基础库使用最新稳定 3.17.x；`manifest.json` 声明、小程序后台「基础库最低版本设置」与实际使用的 API 能力三者一致，使用了高版本 API 必须提供降级或关闭态。
- 主要验证机型覆盖：iPhone（含刘海/灵动岛）、Android 主流（含异形屏）各至少一组真机或模拟器截图；小程序验收不使用 390/375 Web 视口替代。

**D1 数据大屏策略：**

- 设计基准 1920×1080；2560/4K 等高分辨率按等比放大（整体 `transform: scale` 或 rem 等比方案），不重排信息架构。
- 拼接屏/超宽屏（>16:9）保持内容居中并留出背景延伸区，不拉伸图表变形；图表容器使用容器尺寸自适应而非固定像素。
- 大屏不要求触控交互（键盘/鼠标操作）；轮播/自动刷新频率为 Token 可配置项。

**验收证据：** 每个交付模块的 Step 5/6 按上述基线产出八组 Web 视口截图（或视觉回归）＋小程序真机/模拟器截图；像素差异阈值、动态区域豁免与人工批准记录随证据留档（延续 W1 验收包 §5.1 的验证要求）。

### 5.2 显示与格式规范（DEC-20260820-010/011/012/013）

数值与文本的显示格式全端统一，格式化函数收敛到各端 `shared/` 工具（Web 与小程序各一份实现，行为一致），禁止页面内散落 `toFixed`/`toLocaleString`/手写拼接：

- **金额（明细）**：存储为分（整数），显示为元——千分位＋2 位小数＋`¥` 前缀（如 `¥1,234.56`）；订单/流水/账单等明细不做量级换算；充电订单金额分列电费与服务费两栏（各自 ¥ 千分位 2 位）；账户余额、充值、退款金额同明细格式；导出对账文件同格式并在表头注明单位。
- **电量/功率（明细）**：电量 `kWh` 保留 2 位小数（`12.50 kWh`；数据库按 3 位小数存储，对齐国标 GB/T 28569-2024 计量分辨力 0.001 kWh）；功率 `kW` 保留 2 位小数（`60.55 kW`，与量级换算后的 MW/GW 精度一致）；金额、电量、ID 等数字列使用 `--evco-font-number` 等宽 Token。
- **电价/单价**：单位 `元/kWh`；管理端计费配置与分时段单价（尖/峰/平/谷）存储与展示 4 位小数（覆盖 `0.555`/`0.4883` 等现实电价，精度方向对齐《电力市场计量结算基本规则》发改能源规〔2025〕976 号）；用户端展示 2 位小数（仅展示层舍入，结算按存储精度计算，金额四舍五入到分）；服务费单价、补贴单价、平均单价/度电收入指标同此精度（展示 2 位、存储 4 位）。
- **充电时长**：列表与详情用 `1 小时 23 分` 格式；纯数字列可用分钟整数（`83 分钟`）；预计充满/剩余时间用分钟整数（`约 25 分钟`）；报表聚合用小时 1 位小数。
- **电压/电流/SOC**：电压 `V` 整数（遥测明细 1 位小数）；电流 `A` 1 位小数；SOC 为整数百分比；SOC 增速（充电速度）`%/min` 1 位小数。
- **温度/湿度**（电池/枪头/模块/环境）：温度 `℃` 1 位小数（`38.5 ℃`）；湿度 `%` 整数。
- **V2G 放电量**：`kWh` 2 位小数，与充电量分列展示，量级换算同电量阶梯（W8 V2G 模块）。
- **信号强度**：`dBm` 负整数（`-87 dBm`），设备详情展示。
- **评分**：1 位小数＋`分`（`4.8 分`，满分 5）。
- **距离**（找桩/导航）：`km` 1 位小数（`1.2 km`）；不足 1km 用 `m` 整数（`560 m`）。
- **节碳量**：`kg` 保留 1 位小数，聚合达阈值升级为 `t`（见下表）。
- **百分比**：保留 1 位小数（`98.5%`），进度类场景配合语义色；利用率（时间/功率/站点）、在线率、完好率、故障率、订单完成率、退款率等比率类统计指标同为百分比 1 位小数。
- **均值类统计指标**：平均单价/度电收入（`元/kWh` 展示 2 位存储 4 位）、日均充电次数（`次/日` 1 位）、单桩日均充电量（`kWh` 2 位）、平均充电时长（小时 1 位）、MTTR 平均修复时长（小时 1 位）。

**单位与量级换算（充电能源场景统计，DEC-20260820-011）**——总览统计卡、历史报表、图表等聚合场景，按数值大小自动升级单位：

| 维度 | 明细单位与精度 | 换算阶梯（达到阈值即升一级） | 升级阈值 |
| --- | --- | --- | --- |
| 功率 | kW，2 位小数 | kW → MW → GW（换算后 2 位小数） | ≥ 10,000（当前单位） |
| 电量 | kWh，2 位小数 | kWh → MWh → GWh（换算后 2 位小数） | ≥ 10,000 |
| 金额（统计卡/报表聚合） | 元，千分位 2 位 | 元 → 万元 → 亿元（换算后 2 位小数） | ≥ 100 万元；≥ 10,000 万元 |
| 计数（订单/桩/用户数） | 千分位整数 | 个 → 万 → 亿（换算后 2 位小数） | ≥ 10,000；≥ 10,000 万 |
| 节碳量 | kg，1 位小数 | kg → t（换算后 2 位小数） | ≥ 1,000 |

- 换算示例：`12,345.60 kW` → `12.35 MW`；`5,847,291 kWh` → `5,847.29 MWh`；累计营收 `¥2,345,678.90` → `234.57 万元`、`¥1,234,567,890.00` → `12.35 亿元`；`68,240 单` → `6.82 万单`、`123,456,789` → `1.23 亿`。

**换算不变量与展示防溢出（DEC-20260820-013）**：

- **换算不变量**：阈值设计保证任一档位下数值部分 ≤ `9,999.99`（含千分位与小数点共 7 字符），单位标签 ≤ 3 字符（kW/MW/GW/kWh/万元/亿元/万/亿/t）——即格式化后的「数值＋单位」字符串长度有界，前端按最坏字符串预留宽度即可保证永不撑破容器。金额/计数补第二级（万元→亿元、万→亿）正是为维持该不变量；节碳量 `t` 档封顶（9,999.99 t ≈ 万吨级，当前单机部署阶段远达不到，超阈值场景再评估登记 DEC）。
- **统计卡**：值区按最坏字符串（`9,999.99` ＋单位，如 `9,999.99 万元`）预留 min-width；卡片空间不足时依序降级——① 值与单位换行为两行（值上单位下），② 卡片换行/堆叠（`<768` 断点统计卡改双列或单列），③ 仍放不下时缩小卡片内边距与图标区；**字号不得低于排版 Token 最小档（12px），严禁对数值做省略号截断或移出卡片边界**（数字被截断＝数据错误）。
- **表格数字列**：`white-space: nowrap`＋`--evco-font-number` 等宽；数字列 min-width 按最坏字符串设定（约 7 字符＋单位）；列宽不足时按 §5.1 规则横向滚动或卡片化（`<768`），不压缩数字列、不断行。
- **图表**：轴标签含单位（如「功率（MW）」）宽度计入轴区预留；tooltip 数值同 formatter 输出；D1 大屏等比缩放下字符串随容器缩放，无额外溢出风险。
- **验收口径**：八组视口截图须包含至少一张含「接近阈值大值」（如 9,999.99 kW / 999 万元）的统计卡与表格页面，作为防溢出的直接证据。
- 单位统一用 SI 符号阶梯，页面不使用「万kWh/亿kWh」等中文能量单位；监管报送如需万千瓦时等格式，由后端按监管方模板在报送层转换。
- 换算仅作用于展示层：计算、结算、导出对账一律使用基础单位全精度（kW/kWh/元）；换算后数值 ≥1,000 仍加千分位；明细列表金额不换算（统计卡才按阈值转万元）。
- 统计卡按单值独立判断单位；图表（ECharts）坐标轴按该轴数据最大值统一换算并在轴名标注单位（如「功率（MW）」），tooltip 跟随轴单位，禁止同一轴混用两种单位。
- 量级换算实现收敛进 `formatPower`/`formatEnergy`/`formatMoney`/`formatCount`/`formatDuration`（各端 `shared/`，支持明细/统计两种模式），换算阈值常量与 design-tokens 同源维护。
- 数据库存储精度对齐（供后续充电订单/财务 DDL 设计引用）：电量 `decimal(x,3)` kWh、单价 `decimal(x,4)` 元/kWh、金额分为整数。
- **时间**：列表与详情用绝对时间 `yyyy-MM-dd HH:mm:ss`；消息/动态/操作日志用相对时间（`5 分钟前`、`昨天 14:30`，超过 7 天转绝对）；导出文件含时区说明。
- **手机号脱敏**：列表与详情默认 `138****1234`；查看明文需对应 `resource:write` 权限且查看行为记审计日志。
- **雪花 ID**：18 位 ID 列表默认截断显示（前 6 后 4，如 `194829…7301`），点击复制完整值。
- **空值**：统一长破折号 `—`，禁止「无/null/空字符串」混用；空值不参与排序时排最后。
- **国际化**：全部端仅简体中文，不引入 i18n 框架；如未来需要多语言须先登记 DEC。
- **主题与端映射**：`energy-green`=P1/P2 默认；`graphite-night`=P1/P2 用户可选暗色（偏好持久化）；`command-deep`=D1 专用；M1-M4 默认亮色、跟随系统暗色由 wot-design-uni 支持。主题切换不得改变信息架构或状态语义（沿用 design-tokens 既有约束）。
- **语义色**：业务状态色（charging/fault/idle）与通用语义色（success/warning/error/info）分开使用——订单/设备等业务状态用业务色，表单校验/操作反馈/标签用语义色；全部来自 `--evco-status-*` Token，不得使用组件库默认色值直写。

### 5.3 组件与交互使用规范（DEC-20260820-010）

- **表单**：必填字段用 `*` 标记；校验时机为字段 `blur`＋提交时统一校验；错误提示以红色文字内联显示在字段下方，禁止仅用 toast 报校验错误；提交按钮在异步期间禁用并显示 loading。
- **弹层**：Modal 用于确认与简短操作（≤3 个输入）；Drawer 用于详情查看与复杂编辑（>3 个输入或含子列表）；不可逆操作（删除、停用、退款）使用红色主按钮＋后果说明，删除类须输入实体名称确认；含未保存内容的弹层被 Esc/遮罩关闭时须二次确认。
- **消息反馈**：`message` 用于操作即时结果（成功/失败，≤4 秒自动关闭）；`notification` 用于异步任务结果与需停留的通知；弹层内反馈使用弹层内联提示，禁止 message 覆盖在 Modal 上。
- **表格**：默认每页 20 条（可选 10/20/50/100）；操作列固定右侧；斑马纹默认开启；长文本省略号＋悬浮 tooltip；数字/金额列右对齐、文本列左对齐、状态列用语义色 Tag；列宽规则遵循 §5.1（固定列固定、弹性列 min 120/max 360）。
- **加载与空态**：首屏与卡片区加载用骨架屏；按钮提交与局部刷新用 spinner；空状态＝图标＋一句话说明＋主操作引导按钮（如「暂无充电站，去新建」）；403/404/500 提供整页状态与返回操作。
- **细节 Token**：圆角 4px（输入框/按钮）、8px（卡片/弹层）；边框统一 1px；z-index 遵循组件库默认层级并禁止业务代码写 `z-index: 9999` 类魔法数；图标尺寸档位 12/14/16/20/24；动效时长 hover 0.2s、展开/收起 0.3s（ease），必须尊重 `prefers-reduced-motion`。
- **长列表**：滚动加载或行数可能超过 200 的列表启用虚拟滚动；大数据量导出走后端异步导出任务，不在前端全量拉取。
- **小程序组件**：M1-M4 统一使用 wot-design-uni（DEC-20260820-010，Vue3＋TS、CSS 变量主题定制与本项目 design-tokens 契合、暗色模式支持、维护活跃）；Web 端 Element Plus 组件必须经 `packages/ui` 受控封装后才可在业务模块使用，禁止业务代码直接深改组件库内部样式。

## 6. UI、需求与接口协作

每个功能卡片至少关联：菜单/场景编号、原型或状态说明、权限/数据范围、API 契约、异常文案、测试用例。UI 评审以“主流程、加载、空、失败、越权、禁用、移动端/桌面端”逐项截图留证。

REST 只使用版本化资源路径；请求 DTO 与响应 VO 的字段需在 OpenAPI 中有中文说明、必填/范围/枚举/脱敏规则。统一信封、分页、错误码、追踪与幂等规则以《[API 通用接口规范](../api/API通用接口规范-v1.md)》为准；破坏性变更升 API 大版本；事件/MQTT 先登记在根 `contracts/`，不得从 Java 类反推契约。

## 7. 数据库、MyBatis 与迁移

```text
database/
├── mysql/evco_<domain>/migration/VyyyyMMddHHmm__description.sql
└── clickhouse/evco_telemetry/{ddl,materialized-views,backup-restore}/
```

- 一个 Schema 只由其拥有服务迁移和写入；Flyway 仅新增前向迁移，已执行文件绝不修改。
- 每表必须明确主键、审计列、唯一约束、索引、数据分类、留存/删除策略；金额使用最小货币单位整数，时间 UTC，禁止以浮点处理金额或电量。
- Entity 对应本服务表，字段名与列映射明确；Mapper 的查询必须有数据范围、排序和分页上限，更新/删除必须有条件与受影响行数预期。
- SQL 禁止 `SELECT *`、拼接用户输入、无条件更新/删除、跨 Schema 写入。复杂 SQL 放 Mapper XML 或注解旁，必须有中文业务说明和执行计划验证。

| 架构测试 | Java 放在 `src/test/java/.../architecture/`，校验服务 Maven 隔离、业务域包直挂传统分层和跨域禁止依赖。 |
| 集成测试 | Java 放在对应模块的 `integration/` 包并以 `IT` 结尾；覆盖 Mapper、迁移、事务、缓存、外部适配器，优先 Testcontainers 与脱敏夹具。 |

| E2E | 根 `tests/e2e/<app>/<module>/`；只能在 API 自动化与人工门禁通过后覆盖主流程、幂等、越权、失败/补偿和跨端路径。 |
| 性能/安全/恢复 | 根 `tests/{performance,security}/` 与对应 Runbook；按阶段覆盖目标负载、鉴权、故障、备份恢复，Mock 不得替代真实门禁。 |

配置按默认值、非敏感环境覆盖、受控密钥引用分层。仓库只能提交示例键和占位值；每项外部依赖要有超时、重试/退避、幂等、限流/熔断或明确关闭态。所有服务传播 `traceId`，健康检查不泄露内网地址或敏感信息，指标/告警/Runbook 用业务风险命名。

### 8.1 W1 必须落地的质量门禁

W1 的 CI 平台固定为 GitHub Actions，与现行 GitHub 仓库和 Pull Request 流程一致；在工具尚未实际接入前，只能写为“计划门禁”，不得宣称已经启用。每个 Pull Request 至少执行下列检查，任一失败不得合入：

| 范围 | 自动门禁 | 评审门禁 |
| --- | --- | --- |
| Java | Maven Java 21、Spotless 格式化、Checkstyle、ArchUnit、Surefire/Failsafe、JaCoCo；Mockito 必须使用显式 agent 配置或移除对 inline mock maker 的依赖，禁止依赖 JDK 动态挂载 agent。 | 中文 Javadoc/注释的业务准确性、事务、权限、脱敏和异常语义。 |
| 前端 | pnpm、ESLint、Prettier、`vue-tsc`、Vitest；API Client 与 OpenAPI 生成物一致。 | 模块归属、中文注释、页面全状态、可访问性和前端不替代服务端权限。 |
| 契约/数据库 | OpenAPI 与事件/MQTT Schema lint、Flyway 命名及前向迁移校验。 | 字段中文说明、数据分类、兼容性、幂等和失败处置。 |
| 仓库 | Markdown 本地链接、`git diff --check`、敏感文件扫描。 | 无无主 TODO、无过期现役表述、交付证据与变更影响同步。 |

注释缺失检查使用受控脚本只定位缺少中文说明的公开类型、公共方法、模型字段、测试显示名称和关键风险标记；它不能判断注释是否正确，不能以“脚本通过”替代人工审查。
