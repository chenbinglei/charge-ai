# 充电运营平台研发工程规范基线

> 版本：v1.1<br>
> 状态：现役强制规范；W0 服务接缝预留包的先决出口。<br>
> 依据：DEC-20260814-017、DEC-20260814-018。<br>
> 适用范围：需求、后端、前端/UI、契约、测试、数据库、配置、运维和交付资料。

## 1. 目的、优先级与执行方式

本规范在第一行生产代码前统一工程结构和质量边界。它不替代已生效的需求、架构、命名、数据治理和协作规范；冲突时按下列优先级执行：用户批准记录 → 现行交付计划 → 架构/安全基线 → 本规范 → 局部 README。

规范分为两类：

| 类别 | 含义 | 执行方式 |
| --- | --- | --- |
| 自动门禁 | 能由构建或测试确定验证的规则。 | 违反即构建失败；W0 建立最小门禁，W1 接入完整流水线。 |
| 评审门禁 | 需要业务、可读性或运行语境判断的规则。 | PR/模块验收清单逐项留证；未通过不得标记模块完成。 |

禁止为了通过形式检查创建空业务端点、空消费者、空迁移或虚假的测试覆盖。规则无法适用时，必须在 DEC/ADR 中说明原因、替代控制和回归范围。

## 2. 物理目录与所有权

唯一目录结构以《[工程架构与数据分库设计](../design/充电运营平台工程架构与数据分库设计-v1.md#4-当前目录结构)》为准。本节定义各目录可以放什么，防止边界被稀释。

| 目录 | 可放内容 | 禁止内容 |
| --- | --- | --- |
| `backend/services/<service>/` | 单一服务的启动、接口、应用、领域、基础设施和服务内测试。 | 其他服务的业务类、跨服务 Repository/Mapper、硬编码凭据。 |
| `backend/libraries/shared-kernel/` | 无业务归属的 ID、时钟、错误模型、TraceId、审计上下文、幂等键。 | 领域实体、DTO、Mapper、业务枚举和“万能工具箱”。 |
| `backend/libraries/contracts/` | 从根 `contracts/` 生成或映射的版本化传输模型。 | 手写并绕开源契约的业务协议。 |
| `backend/libraries/testkit/` | 测试夹具、Testcontainers、架构/契约测试支持。 | 生产业务逻辑和真实凭据。 |
| `frontend/apps/<app>/` | P1、P2、M1–M4、D1 各端页面、路由、端内状态和端内测试。 | 其他端的页面复制品、未授权跨端业务状态。 |
| `frontend/packages/` | UI、设计令牌、类型、由 OpenAPI 生成的 API 客户端。 | 直接调用后端数据库、业务页面或未经登记的第三方 SDK。 |
| `database/` | 按拥有者 schema 放置的前向 Flyway 迁移、ClickHouse DDL、备份恢复资料。 | 跨 schema 写入、可执行迁移中的真实数据/凭据。 |
| `contracts/{openapi,events,mqtt}/` | 版本化接口、事件、MQTT Schema 和目录。 | 未登记的运行时协议或未来外部生态空契约。 |
| `tests/` | 跨服务的 unit、integration、contract、e2e、performance、security 测试。 | 仅为覆盖率存在、无断言或依赖生产凭据的测试。 |
| `platform/` | 基础设施编排、可观测性、部署和 Runbook 对应资产。 | 业务源代码、个人环境文件或密钥。 |
| `docs/`、`delivery/` | 需求、设计、规范、用户资料、验收与交付证据。 | 与现役事实冲突但未标为历史的副本。 |

## 3. 后端与契约编码规则

每个 Java 服务固定采用传统的 `controller`、`service`、`mapper`、`entity`、`dto`、`vo` 分层；`platform-service` 在各层下按既定业务模块再分包。当前 Maven/Java 根命名空间固定为 `com.elink.evco`。包职责、依赖方向、命名、中文注释和模板以《[全栈研发工程规范](全栈研发工程规范-v1.md)》为强制细则。
- 跨服务同步协作只经本服务 `client` 端口和可替换适配器；跨服务异步协作只经版本化契约与批准后的 Outbox/Inbox。禁止 Maven 直接依赖其他服务、直接访问其他 schema、复制对方领域实体。
- 对外 REST、事件、MQTT 的事实来源必须先登记于 `contracts/`；破坏性变化新建大版本，已发布版本不得静默改变语义。
- 错误使用统一问题响应和稳定错误码；日志必须包含 `traceId`，不得记录凭据、身份证件、完整手机号、支付数据或原始敏感报文。

命名、时间、金额、事件、Topic、配置键与迁移格式严格遵循《[平台技术命名规范 v1](平台技术命名规范-v1.md)》。

## 4. 注释、可读性与 AI 生成内容

- 代码表达“做什么”；注释只说明不能从代码直接推出的“为什么”、业务约束、外部协议差异、并发/事务边界或安全风险。
- 公共类/公共方法、状态机、金额/结算计算、权限规则、补偿逻辑和外部适配器必须说明输入、输出、不变量、失败语义及幂等语义。
- 禁止注释复述代码、保留失效 TODO、用注释屏蔽问题，或将需求讨论、凭据和个人信息写入注释。
- AI 生成的生产变更与人工代码同等接受测试、可读性和安全审查；提交说明或完成记录要能追溯需求、契约、测试和人工复核，不以“AI 已生成”作为通过理由。

## 5. 前端、UI 与交互规则

- 七端分别维护在 `frontend/apps/`；可复用视觉基础只进入 `packages/ui` 和 `packages/design-tokens`，业务流程不抽成无归属的共享组件。
- 色彩、字型、间距、圆角、阴影、断点和状态样式从设计令牌取得；不在页面散落魔法数。新令牌先在设计系统登记。
- 页面必须具备加载、空、错误、无权限、关闭态和网络降级状态；实时页面还显示最后更新时间和重连/降级提示。
- 页面权限只能反映服务端已授权事实；M1 的公众可用性遵循应用/渠道/业务资格规则，不能被 P1 页面权限替代。
- 前端仅通过版本化 API 客户端访问后端；不得在浏览器保存密钥、直接访问数据库、伪造服务端权限判断或把敏感数据写入埋点。
- 新页面或关键变更须有桌面和移动端截图证据，键盘可达、可读标签、焦点状态和对比度纳入 UI 评审。

## 6. 测试与质量门禁

| 层级 | 责任 | 最小要求 |
| --- | --- | --- |
| 单元测试 | 聚合、值对象、状态机、金额、权限和映射逻辑。 | 快速、确定性、无网络；断言正常、边界、幂等和失败分支。 |
| 架构测试 | Maven 模块和 Java 传统分层边界。 | W0 即执行：服务互不依赖，Controller 不直连 Mapper/Entity，Service 不依赖 Controller/VO，Mapper 不依赖上层传输模型。 |
| 集成测试 | Repository、迁移、缓存、外部适配器和事务。 | W1 起按需使用 Testcontainers，测试独立且可重复。 |
| 契约测试 | OpenAPI、AsyncAPI/Kafka、MQTT 和客户端兼容性。 | W1 起：变更必须匹配登记契约和版本策略。 |
| E2E | 用户关键流程、跨端、权限、异常、补偿和受控外部依赖。 | API 门禁后开始前端；模块出口必有证据。 |
| 性能/安全/恢复 | 目标负载、越权、依赖故障、备份恢复。 | 按 W4/W6/W10/W12 分阶段引入；不得以 Mock 宣称真实容量或外部能力通过。 |

覆盖率是发现遗漏的信号，不是质量替代物；关键风险用场景断言证明。测试名称以行为和预期结果命名，夹具脱敏且可重复，禁止依赖执行顺序或实时生产数据。

## 7. 数据库、数据与迁移规则

- Schema 只由拥有服务维护；迁移为前向、可审计、可回滚说明的 Flyway 文件，绝不改写已执行迁移。
- 建表必须定义主键、审计列、访问路径索引、唯一/状态约束、数据分类和留存/删除策略；金额、电量、时间和命名按技术命名规范。
- Repository 查询必须携带数据范围、排序和分页边界；禁止 `SELECT *`、无条件更新/删除、拼接用户输入的 SQL 与跨 schema 读写。
- JSON 只能存受控扩展；结算、权限、查询与审计事实必须显式建列。删除、导出、脱敏和密钥管理服从《[数据治理与密钥管理矩阵](数据治理与密钥管理矩阵-v1.md)》。

## 8. 配置、可观测性与运维规则

- 配置按默认值、环境非敏感覆盖和受控密钥引用分层；代码库只保存示例键与占位符，绝不保存真实值。
- 每个服务必须有存活、就绪和依赖降级状态；健康检查不得泄露内部地址、凭据或业务敏感信息。
- 所有入口传播或生成 `traceId`；审计记录行为主体、动作、对象、结果、时间和关联 ID。日志采用结构化字段并按数据治理规则脱敏。
- 指标、告警、仪表盘、运行手册和恢复步骤以业务风险命名；订单、资金、登录和控制优先于分析/导出/低优先级任务。
- 新外部适配器必须具备超时、重试/退避、幂等、限流、熔断或明确关闭态；真实渠道/设备/监管验收仍按现行 C1/C2/C3-R 和模块门禁执行。

## 9. 需求、交付证据与变更

- 每项实现从需求菜单/场景映射到验收条件、契约、迁移、测试、Runbook 与完成记录；缺一项不得标记完成。
- 需求文档放 `docs/requirements/`，架构与 ADR 放 `docs/design/`，规范放 `docs/standards/`，API/协议事实放 `contracts/`，客户验收证据放 `delivery/acceptance/`。
- 范围、日期、冻结模块、真实渠道启用、架构例外和破坏性变更先登记审批日志；已完成模块的修改必须带兼容策略与回归范围。
- Git/SVN、敏感信息检查、提交说明与外网待同步规则遵循《[单人 AI 协作开发与变更治理规范](单人AI协作开发与变更治理规范-v1.md)》和根目录 `AGENTS.md`。
