## 1. 目的、优先级与执行方式

本规范是工程结构的**基线索引**：§2 目录所有权表是唯一权威；各域实施细则不在本文重复，统一按 §3 索引引用对应权威规范，避免多口径。冲突时按下列优先级执行：用户批准记录 → 现行交付计划 → 架构/安全基线 → 本规范 → 各域细则规范 → 局部 README。

| 类别 | 含义 | 执行方式 |
| --- | --- | --- |
| 自动门禁 | 能由构建或测试确定验证的规则。 | 违反即构建失败；细则见《[全栈研发工程规范](全栈研发工程规范-v1.md)》。 |
| 评审门禁 | 需要业务、可读性或运行语境判断的规则。 | 按门禁映射由评审子代理只读会签留证；细则见《[开发流程总纲](开发流程总纲-v1.md)》。 |

禁止为了通过形式检查创建空业务端点、空消费者、空迁移或虚假的测试覆盖。规则无法适用时，必须在 DEC/ADR 中说明原因、替代控制和回归范围。

## 2. 物理目录与所有权

唯一目录结构以《[工程架构与数据分库设计](../design/充电运营平台工程架构与数据分库设计-v1.md#4-当前目录结构)》为准。本节定义各目录可以放什么，防止边界被稀释。

| 目录 | 可放内容 | 禁止内容 |
| --- | --- | --- |
| `backend/services/<service>/` | 单一服务的启动、技术配置、业务模块传统分层、服务内技术支撑和测试。 | 其他服务的业务类、跨服务 Repository/Mapper、硬编码凭据。 |
| `backend/libraries/shared-kernel/` | 无业务归属的 ID、时钟、错误模型、TraceId、审计上下文、幂等键。 | 业务实体、DTO、Mapper、业务枚举和“万能工具箱”。 |
| `backend/libraries/contracts/` | 从根 `contracts/` 生成或映射的版本化传输模型。 | 手写并绕开源契约的业务协议。 |
| `backend/libraries/starter/` | evco-starter 跨服务 web 通用能力：基础层（链路追踪、全局异常、MyBatis 通用拦截器）；管理端层（Bearer 鉴权、两档权限拦截，`evco.web.security.enabled` 开关控制，默认开启）。 | 业务实体、DTO、Mapper、业务枚举等任何业务归属代码；绕开开关的服务内重复鉴权组件。 |
| `backend/libraries/testkit/` | 测试夹具、Testcontainers、架构/契约测试支持。 | 生产业务逻辑和真实凭据。 |
| `frontend/apps/<app>/` | P1、P2、M1–M4、D1 各端页面、路由、端内状态和端内测试。 | 其他端的页面复制品、未授权跨端业务状态。 |
| `frontend/packages/` | UI、设计令牌、类型、由 OpenAPI 生成的 API 客户端。 | 直接调用后端数据库、业务页面或未经登记的第三方 SDK。 |
| `database/` | 按拥有者 schema 放置的前向 Flyway 迁移、ClickHouse DDL、备份恢复资料。 | 跨 schema 写入、可执行迁移中的真实数据/凭据。 |
| `contracts/{openapi,events,mqtt}/` | 版本化接口、事件、MQTT Schema 和目录。 | 未登记的运行时协议或未来外部生态空契约。 |
| `tests/` | 跨服务的 unit、integration、contract、e2e、performance、security 测试。 | 仅为覆盖率存在、无断言或依赖生产凭据的测试。 |
| `platform/` | 基础设施编排、可观测性、部署和 Runbook 对应资产。 | 业务源代码、个人环境文件或密钥。 |
| `docs/`、`delivery/` | 需求、设计、规范、用户资料、验收与交付证据。 | 与现役事实冲突但未标为历史的副本。 |
