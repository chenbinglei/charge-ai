# 文档可读性与术语说明规范

> 版本：v1.0
> 状态：现役工程规范。
> 目的：让非该领域读者能知道“这是什么、为什么存在、谁负责、失败怎么办”，同时不把每份文档写成重复的教科书。
> 适用：`docs/`、`contracts/`、服务 README、`delivery/` 的现役 Markdown 和管理汇报材料；`archive/` 保持历史原样。

## 1. 基本原则

1. **解释概念，不逐行堆注释。** 每个文档要让目标读者能理解决策和边界；代码、Schema、配置仍应在复杂规则、非常规取值和安全边界处写局部注释。对代码类型、字段、方法和模型的强制中文说明，以《[全栈研发工程规范](全栈研发工程规范-v1.md)》为准；本条不降低其要求，只禁止语法逐行翻译。
2. **首次出现先说白话。** 非通用缩写、服务名、Topic、消费者组、状态名和指标在首次出现处写中文含义，或明确链接到权威术语页。
3. **一处权威，其他处链接。** 不复制完整 Topic、状态机或字段表；摘要只说明用途、边界和权威来源，避免版本漂移。
4. **写“为什么”和“失败后怎么办”。** 仅列组件或流程不合格；必须说明所解决的风险、责任方、失败状态、人工入口或 Go 门禁。
5. **不写敏感值。** 示例和说明不得出现真实密钥、证书、账号、生产地址、个人信息或未脱敏业务报文。

## 2. 现役文档的最低结构

除短 README 外，现役架构、需求、契约、运行和管理文档开头应包含：

| 要素 | 要回答的问题 |
|---|---|
| 状态与适用范围 | 这是草案、实施权威、管理摘要还是历史资料？谁该读、谁不该拿它实施？ |
| 先读什么 | 对不了解背景的人，前置的权威文档是什么？ |
| 术语/图例 | 缩写、服务、状态、箭头、颜色或表格列分别代表什么？ |
| 决策与原因 | 为什么采用该边界/流程，而不是把责任混到其他服务？ |
| 风险与失败处理 | 什么不能自动恢复，谁告警、谁审批、何时禁止上线？ |
| 权威链接与证据 | Schema、状态机、测试、压测或执行台账在哪里？ |

## 3. 契约和事件文档的额外要求

每个 API、MQTT Topic、Kafka Topic、消费者组和状态机须明确：

- 用一句白话说明业务目的；
- 发布者、消费者、消费者组用途与业务事实所有者；
- 请求/事件 key、局部顺序、幂等键、重试、超时、DLQ 和是否允许重放；
- 字段的来源、类型、数据分类和禁止放入报文的敏感数据；
- 成功、失败、超时、重复、乱序和人工处理的状态；
- 对应 Schema、自动化测试、E2E 或生产 Go 证据。

对 Kafka 的通俗说明统一链接《[事件协作与 Kafka 通俗说明](../design/事件协作与Kafka通俗说明-v1.md)》；Topic 的精确字段仍链接《[Kafka 事件目录](../../contracts/events/README.md)》。

## 4. 图表、管理汇报与代码注释

- 图表必须有标题、范围、图例和“未表达什么”；架构图不可用一根箭头掩盖同步 API、异步事件、设备协议和数据所有权的区别。
- 管理汇报必须标注为摘要、列出权威来源和关键上线门禁；不得把“模拟成功”“目录已建”写成生产已接入、容量已签发或真实 V2G 已开放。
- 代码在公开接口、状态迁移、金额/计量计算、并发/幂等、权限、安全校验和反直觉取值处必须解释意图与不变量；不要为显而易见的语法重复写注释。
- Schema 枚举、状态和金额/时间字段应有 `description`，说明业务含义、单位、允许来源和隐私限制。

## 5. 审核门禁

新增或修改现役文档时，作者在提交前核对：术语是否可理解、图/表是否自解释、是否链接唯一权威、是否写明责任与失败处理、是否泄露敏感信息。涉及支付、退款、设备控制、双模式、监管、V2G、数据导出或恢复的文档，还必须同步高风险契约、数据治理或执行台账中的相应证据。
