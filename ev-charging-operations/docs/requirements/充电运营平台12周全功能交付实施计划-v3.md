## 1. 不可变目标、日历与权限

- 2026-09-25 至 2026-10-07 不安排开发，其中包括中秋假期、国庆假期及额外指定休假。承诺开发产能为 60 个承诺工作日，截止 2026-11-19；周末不计入承诺产能。
- 11 月 20 日是现行 106 项的目标上线日，不是删减范围、跳过测试或把未完成模块标记完成的授权。进度不足时，必须由唯一批准人决定延期、额外加班或新增功能的处理；系统不得自行砍功能、缩短门禁或改变上线范围。
- 周末如实际投入，只能提前启动既定模块、补回归或处理已批准新增项，不改变模块内的固定顺序和完成标准。
- 所有真实凭据仅能在受控系统及 P1 授权页面中维护；不得出现在 Git、日志、导出、文档或聊天。

## 2. 固定模块门禁

每个模块必须严格依次完成：

`需求/验收确认 → 后端、迁移、契约实现 → API 自动化与人工验证通过 → 前端实现 → 前后端 E2E、权限与异常验证 → 完成记录、文档同步、提交与审查`

1. 前端绝不在对应 API 门禁通过前开工；API 阶段与 E2E 阶段各测试一次。
2. 后端阶段包含业务模型、传统分层 Service 实现、数据库迁移、数据范围、审计、错误码、Outbox/补偿及所需 MQTT/事件契约。
3. API 阶段必须有 OpenAPI/MQTT/事件契约、单元/契约/集成自动化测试和人工验证；重点覆盖常规、幂等、越权和异常。
4. E2E 阶段覆盖主流程、关键异常、适用的独立/IOT 协同模式、跨端流程与受控模拟或真实外部依赖。
5. 完成后，在执行台账登记版本、迁移、接口、测试、验收、Runbook 和已知限制；模块即进入冻结状态。

## 4. 小程序、登录与支付渠道

M1 是面向公众、渠道中立的个人充电产品。微信小程序和未来支付宝小程序共享同一个人用户、订单、钱包、权益、发票和 V2G 业务事实及 API，不建设两套业务平台。P1 不管理 M1 个人用户的页面或功能权限：小程序管理中的应用生命周期、内容、已批准业务开关和灰度投放都不是角色/页面授权；个人用户是否能交易仅由登录、账户状态、支付/余额、实名、V2G 授权等业务校验决定。

- 个人用户主档是 M1 登录链路的权威业务事实，必须在 W2 交付，而不是等到 W6 的运营页面：渠道身份授权成功后，服务端以“渠道 + 应用实例 + 外部主体标识”保证身份映射唯一，并用经验证、规范化的手机号匹配既有个人用户；命中则幂等更新身份绑定和登录资料，未命中才创建个人用户主档。渠道身份已绑定他人、手机号命中人工锁定/冲突用户或授权资料不完整时，必须拒绝自动合并并形成可审计的人工处置事项。
- M1 微信登录：微信身份授权 → 用户授权手机号 → 服务端验证、创建或更新个人用户主档及微信身份映射 → 平台登录态。未授权手机号可浏览公开站点，但不得交易、退款、核销、申请发票或使用 V2G。支付宝渠道遵循同一主档和映射规则。
- 同一经验证手机号命中既有个人用户时复用既有账户，不重复创建钱包、订单或权益；手机号变更、身份解绑/重绑、账户冻结和冲突处置由 P1「个人用户」运营流程处理并保留审计。M1 不提供渠道身份的自助绑定、解绑或合并页面；具体 DDL 和 API 契约在 W1 评审后冻结。
- W1/W2 必须冻结个人身份与会话安全契约：授权码仅由服务端向渠道校验/换取，手机号不信任客户端传值；覆盖会话失效、限流、防重放、冲突人工处理、最小收集、隐私告知/同意版本、加密脱敏、访问/导出审计及保留/删除规则。
- M1 可用性按“应用发布状态 → 渠道健康状态 → 已批准业务开关 → 场站营业/开放对象 → 用户业务资格”依次判定；这不是页面权限。公开访客只能浏览对公众开放且营业中的站点，应用停用或渠道故障须有明确关闭态和既有会话处置。
- P1「小程序管理」维护微信/支付宝应用实例、AppID、环境、启停、版本、业务开关、身份授权配置、密钥受控录入、域名/回调检查与审计。
- P1「支付渠道与路由」维护微信/支付宝商户引用、AppID 绑定状态、凭据受控录入、支付/原路退款能力、回调、环境路由、健康度、对账与审计。每笔外部支付意图固化渠道、应用实例、商户引用和路由版本快照；外部退款只使用原支付路由。钱包支付订单的退款先恢复其来源资金批次，后续配置变更不得影响历史交易或退款归属。
- 个人钱包不得只保存汇总余额：每笔现金充值必须形成可追溯的充值资金批次，固化原支付交易、渠道、应用实例、商户引用/路由版本、实收金额、已消费/冻结/已退款及可退款余额。赠送金、红包、积分等非现金资产独立建账，不得作为现金退款来源；钱包扣款、释放和退款须按确定分配规则关联资金批次。
- 商户迁移只为新交易启用新商户。旧商户停止新收款后，保留历史交易查询、原路退款和对账能力及充足退款资金；历史现金充值只能按其原商户路由退款，不得改由新商户退款。旧商户仅在历史可退款余额、退款处理中交易及对账差异全部清零或已有经批准的处置方案后才可关闭。
- 租户结算只由充电订单及其场站结算方案快照决定，与个人充值商户和资金批次解耦。未消费现金充值退款只影响个人钱包、原支付商户和渠道对账，不调整租户结算；充电订单退款、差额退款或后续价格修正必须生成可追溯的租户结算调整。未锁账单可按调整重算，已锁定或已付款账单只能追加调整/追补记录，不得回写历史账单。
- 微信是本期必须真实测试和上线的渠道。支付宝的应用配置、身份/支付抽象、模拟器和关闭态属于本期能力；未来支付宝小程序发布或真实支付联调须由用户批准变更后执行，且只追加渠道适配和渠道 E2E，不重做业务模块。
- 在用户尚未提供微信/商户注册认证资料时，先以版本化渠道适配器、确定性 Mock、脱敏夹具和失败/超时/重复回调场景完成内部 API 与 E2E。Mock 只满足开发门禁，不能标记 C1-W/C2-W 完成，也不能替代真实渠道上线验收。

## 8. V2G 前置预留

V2G 不在 W11 从零开始：W3 资产/指标目录预留双向能力和正反向电量；W4 遥测/控制支持放电方向；W5 订单契约预留独立放电会话和状态机；W6 资金模型预留独立用户 V2G 收益余额；W10 分析/D1 预留 V2G 指标。W11 只完成模拟授权、模拟执行、模拟订单、模拟收益、风控和跨端 E2E；不得产生真实放电控制、真实电量结算或可支取收益。真实现场试点必须另行批准设备/车辆/并网与安全方案、受控场站、现场 E2E、回退与停止预案。提现申请、付款、回单及提现记录保持待定关闭态。放电不得以负数充电订单、个人钱包、企业预存或电卡余额替代。

## 9. 测试、No-Go 与上线门禁

- W1 起执行 GitHub Actions 的格式、静态分析、传统分层架构、中文注释缺失、迁移、单元、契约和文档链接检查；Mockito 不得依赖未来 JDK 将禁止的动态 agent 挂载。W4 起设备 E2E；W5 起交易 E2E；W6 起支付安全与资金一致性；W10 起分析跨端一致性；W12 完成全量 E2E、性能、安全、Kafka 积压恢复、WebSocket 断线恢复、备份恢复、回滚、UAT 与迁移演练。
- 每周出口必须具备：当周菜单覆盖记录、P0/P1 缺陷为零、API/E2E/越权/审计/补偿证据、前向迁移与回滚说明、Runbook 与用户/API 文档。
- C1-W、C2-W、C3-R（目标省市监管真实接入）和小程序订阅消息等真实渠道验证与 Mock 验证分别留证。Mock 通过可证明内部功能，不得将真实渠道门禁标记完成；W12 生产 Go 前必须完成微信登录、支付、结果通知、原路退款和目标省市监管的真实报送/回执/对账 E2E，未完成即作为 No-Go 提交用户决定。
- W6/W8/W12 必测商户迁移和结算边界：旧商户充值后切换商户的历史退款、新商户充值、多资金批次部分消费/退回、未消费充值退款不影响租户结算、充电订单退款/补差生成结算调整，以及已锁定或已付款账单不被回写。
- 出现 No-Go 时，主实现智能体在两个工作日内提交事实、影响、可选延期日期、可用加班方案及新增功能处理建议；只有用户批准后执行。未批准时保持当前模块，不自行开始后续模块。
- W12 只处理缺陷、配置、迁移、UAT 和上线演练；不接收未批准的新功能。

## 10. W12 后的外部生态与能源调控扩展

虚拟电厂及其他第三方平台的授权数据共享、MQTT/HTTP 等协议接入、整站或设备调控、SOC/设备能力/订单约束计算不属于本计划的 106 个菜单范围或 60 个承诺工作日。它们必须排在 W12 发布就绪之后，作为对现行 `ecosystem-service` 的独立扩展启动；不得占用 W10 监管内部就绪，也不得提前创建外部生态 Topic 或空消费者。

国内省市监管仍由 `ecosystem-service` 在 W10 达到内部就绪，真实目标接入另以 C3-R 生产 Go 完成。后续扩展的服务边界、控制优先级、P1 配置和启动门禁见《[监管与外部生态能源协同方案](../design/监管与外部生态能源协同方案-v1.md)》。
