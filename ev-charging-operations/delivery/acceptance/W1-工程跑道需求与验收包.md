## 1. 审核目的与当前边界

本包用于冻结 W1 的工程底座、质量门禁、契约/数据评审范围和后续模块的共同约束。W1 不交付业务页面或业务流程，不以空接口、空迁移、空 Topic、空消费者或 README 占位作为完成证据。

W0 服务接缝预留包已验证，但不等同于 W1 解锁。当前只允许执行 W1 Step 1；本包经用户审核通过后，才可进入 Step 2「契约、DDL 与技术设计」。

本模块遵循：

`Step 1 需求与验收 → Step 2 契约/DDL/技术设计 → Step 3 工程与后端门禁 → Step 4 工程底座前端/测试 → Step 7 完成留证`

W1 的 Step 4 只验收前端/测试工程底座、设计 Token 和可运行样例，不验收任何业务页面。

## 2. W1 范围

### 2.1 工程资产

1. GitHub Actions：后端、前端、契约、迁移、文档、敏感信息和差异检查纳入 PR 门禁。
2. 后端：Java 21、Maven 模块边界、传统业务模块分层、中文注释、统一 API、TraceId、审计和幂等基础。
3. 前端：pnpm workspace、Vue 3 + TypeScript + Vite + Pinia + Element Plus + ECharts 的工程入口；共享类型、API Client、设计 Token 和测试入口。
4. 测试：unit、integration、contract、e2e、performance、security 的可执行目录与最小运行入口。
5. 运行环境：Docker Compose 可重复启动的工程依赖、健康检查、资源限制、配置模板和敏感配置边界。
6. 数据库：Flyway 前向迁移入口、命名规则、Schema 所有权、迁移检查和回滚/补偿说明；不创建未经审核的业务迁移。
7. 契约：OpenAPI、AsyncAPI/JSON Schema、MQTT Topic/ACL 和版本兼容检查；契约为生成客户端和测试数据的唯一输入。
8. 文档：本包、Step 2 设计包、Runbook、质量门禁说明和本地链接均可追溯。
9. Kafka 工程跑道：以 Compose profile、共享客户端配置、事件信封、幂等/DLQ 测试工具、健康检查和契约校验接入工程底座；不创建业务 Topic、业务生产者或业务消费者。

### 2.1a 工程版本矩阵与可重复性

W1 不能只写“使用某技术”，必须把版本、镜像、包管理器和运行参数固定为可复现的矩阵。版本尚未填满或无法在干净环境复现时，W1 不得通过。

| 类别 | 基线要求 | 冻结方式 |
| --- | --- | --- |
| Java/Maven | Java 21 LTS；Maven 使用项目 Wrapper 或固定版本 | `.java-version`/Wrapper、CI 与本地一致 |
| Node/pnpm | 组织批准的 Node LTS；pnpm 固定精确版本 | `.nvmrc`/`engines`/`packageManager`，禁止使用当前机器版本漂移 |
| Web/小程序 | Web 使用 Vue 3 + Vite；小程序使用 uni-app；共享类型/API/Token 独立 | workspace 包边界和构建矩阵 |
| 关系库 | MySQL 8.4/InnoDB，字符集、排序规则、时区和 binlog 策略固定 | Compose 镜像 digest、数据库启动检查 |
| 消息/IoT | Kafka KRaft、EMQX、Redis 的确切版本、协议和资源参数固定 | Compose profile、镜像 digest、健康检查 |
| 分析/对象存储 | ClickHouse、MinIO 的确切版本、保留和备份策略固定 | Compose profile、Runbook、镜像 digest |
| 契约 | OpenAPI 3.1、JSON Schema 2020-12、AsyncAPI/MQTT Schema 版本固定 | lint、兼容性校验和生成工具版本锁定 |
| 环境 | UTC、UTF-8、中文 locale、确定性随机种子、行尾和时钟同步规则固定 | `.editorconfig`、容器环境、CI 检查 |

所有版本必须在 Step 1 评审记录中填入确切值；“latest”“3.x”“5.x”不能作为验收依据。

### 2.1b Web 与小程序工程边界

| 端类型 | 技术基线 | 允许复用 | 禁止复用 |

### 2.3 Kafka 工程跑道集成边界

W1 要集成 Kafka 的工程能力，但不提前实现任何业务事件流。验收至少包括：

- Compose 中提供可重复启动的 Kafka 工程 profile、健康/就绪检查、资源限制和关闭说明；具体 broker 版本、端口和持久化策略在 Step 2 固定。
- 共享生产者/消费者配置：超时、重试退避、批量、手动提交、最大轮询间隔、消费者组命名和优雅停机。
- 公共事件信封和消息头：`eventId`、`eventType`、`eventVersion`、`occurredAt`、`traceId`、`idempotencyKey`、`producer`、租户/工作空间范围和 Schema 版本。
- 统一幂等、重试、DLQ、重放和人工处置接口；工程 Testkit 能验证重复投递、乱序、过期、失败重试和 DLQ 转移。
- Kafka readiness、积压/消费延迟、重试和 DLQ 指标，以及日志中的 TraceId、事件 ID 和脱敏约束。
- AsyncAPI/JSON Schema lint、兼容性检查和契约生成入口；没有登记在事件目录中的业务 Topic 不得创建。

本阶段允许工程测试 Topic 或隔离 Testkit，不允许创建 M1、P1、监管、V2G、VPP 或其他业务 Topic、生产者、消费者和运行时流程。

### 2.4 API、租户、安全与幂等基线

W1 以《[API 通用接口规范 v1](../../docs/api/API通用接口规范-v1.md)》为唯一 HTTP 外观来源，补齐以下可执行规则：

- `tenantId`、workspace、数据范围、操作者和 TraceId 在 HTTP、Kafka、审计和异步任务中的传播与校验。
- 网关认证、服务间认证、CORS、CSRF、CSP、安全响应头、请求体大小、限流、超时、熔断和关闭态。
- `X-Idempotency-Key` 的主体/接口作用域、请求摘要、TTL、重复响应、冲突响应和敏感结果脱敏。
- UUID/ULID、事件时间、接收时间、时钟偏差和时间展示时区的统一规则。
- 错误码注册表、模块编号、HTTP 状态映射、可重试标记和人工处置提示。
- 跨租户读写、IDOR、越权导出和服务端权限绕过必须有自动化失败测试。

### 2.5 数据库、迁移、备份与恢复基线

- 每个业务 Schema 由唯一服务拥有；所有业务表明确 `tenant_id`（适用时）、审计列、版本列、数据分类、留存/删除策略、唯一键和索引。
- 迁移采用 `VyyyyMMddHHmm__description.sql`，只允许新增前向迁移；不使用 down migration，回退通过补偿迁移、代码回退或恢复演练完成。
- MySQL 事实、ClickHouse 遥测、Redis 最新状态、MinIO 原始证据的写入边界、TTL、备份和恢复方式必须分开定义。
- `outbox_event` 与 `inbox_event` 由拥有服务维护；事实写入、Outbox、Inbox 和 offset 提交的事务边界必须可测试。
- 必须提供脱敏初始化、数据库重置、备份、binlog/PITR、恢复验证和失败清理脚本；不得把测试数据或凭据写进迁移。

### 2.6 Compose、配置与可观测性基线

Compose 至少定义 `core`、`iot`、`telemetry`、`observability` 四类 profile，并写明必启服务、可选依赖、资源上限、健康依赖、关闭态和最小机器要求。所有服务必须区分 liveness/readiness，启动失败要 fail-fast 或进入明确关闭态。

统一可观测性至少包括 OpenTelemetry Trace/Metric/Log、TraceId/EventId/CommandId/OrderId 关联、Kafka lag/DLQ、数据库慢查询、连接池、错误率、延迟和资源水位；每个告警必须有责任人、阈值、Runbook 和恢复验证。

配置分为默认非敏感值、环境覆盖和受控密钥引用；仓库不保存凭据。日志禁止完整手机号、证件、支付数据、原始敏感报文和密钥。

### 2.7 测试、供应链与质量量化

- 后端优先 Testcontainers 验证 MySQL、Kafka、Redis、EMQX 等真实协议边界；前端使用确定性 Mock，不能依赖线上服务。
- changed-line coverage、关键资金/权限/幂等/状态机代码覆盖率、契约覆盖率和视觉回归阈值必须在 Step 1 记录确切值；覆盖率不能替代场景断言。
- CI 禁止用自动重试掩盖 flaky test；失败测试必须隔离、登记责任人和修复期限，禁止带病合入。
- GitHub Actions 固定 commit SHA；Maven/Node 依赖锁定；执行 SAST、依赖漏洞、许可证、容器镜像和 SBOM 扫描。
- 构建产物、测试报告、SBOM、镜像摘要和审计日志保留期限、访问权限和下载方式必须明确。

## 5. 多主题与响应式基线（待用户审核）

此前高保真稿仅作为外部视觉预览，未视为生产设计或验收证据。W1 只冻结可实现的设计 Token 和切换约束，不开发业务页面。

建议首批保留三个主题候选：

1. `energy-green`：浅色运营管理后台，以能源绿为主色。
2. `graphite-night`：深色监控工作台，以蓝黑和青色高亮为主色。
3. `command-deep`：深邃蓝数据大屏，以半透明面板和数据发光为主色。

三种主题必须满足：

- 同功能、同信息层级、同布局语义，仅替换 Token，不复制业务组件。
- 充电中、故障、离线、空闲等状态语义保持一致，状态色不得被主题任意改变。
- 以 1920×1080 为主验收视口，同时支持 1440、1024、768 及移动端自适应。
- 栅格为 24 列，间距为 8px 倍数；数字/金额使用等宽字体 Token。
- 支持高对比度、键盘可操作、表格横向滚动和移动端卡片化策略。
- 主题偏好保存范围、默认主题、权限无关性和恢复策略必须写入前端设计说明。

如用户不批准三个候选主题，Step 2 前应指定主题数量、名称和优先级；在此之前不生成主题业务页面。

### 5.1 排版、布局与响应式验收基线

主题只改变 Token，不改变信息架构和布局骨架。W1 必须先冻结以下可实现规则：

- 画布与容器：以 1920×1080 为主验收视口；桌面内容最大宽度 1440px 并居中，1440px 笔记本全宽；主容器内边距、卡片间距和栅格间距均为 8px 倍数。
- 栅格与骨架：24 列栅格、默认列间距 24px；运营后台采用侧栏 + 顶栏 + 内容区；侧栏默认 210px，折叠态 64px；顶栏、内容区最小高度和密度必须使用布局 Token。
- 排版：中文字体栈、H1/H2/正文/辅助文字字号与行高、数字/金额等宽字体、字重、截断和 Tooltip 规则必须定义为 Token，不在页面内散落硬编码。
- 排版候选基线：H1 20/28、H2 16/24、正文 14/22、辅助文字 12/18；顶栏 64px、侧栏 210px/折叠 64px、工具栏 40px、表格正常行 48px/紧凑行 40px、触控目标不小于 44px；最终值必须经用户审核后写入 Token。
- 信息密度：数据卡片按内容自适应高度，不用固定等高制造大块空白；表格行高、工具栏高度、分页间距、卡片内上下留白需有正常/紧凑两档。
- 断点重排：`>=1920` 居中最大宽度 1440；`1440–1919` 全宽布局；`992–1439` 保持侧栏展开并压缩列宽；`768–991` 侧栏折叠为 64px、表格横向滚动；`<768` 表格转卡片列表、双列转单列、操作区换行。
- 内容安全：标题单行省略、地址两行省略、数值不换行；窗口缩放不得出现横向溢出、遮挡、重叠或不可访问操作；空态/错误态/无权限态/禁用态仍保持相同骨架。
- 交互与可访问性：主题切换不改变布局，键盘焦点、Hover、禁用、加载和高对比度状态有明确 Token；触控目标和表格操作在移动端可完成。
- 可访问性：正文与背景达到 WCAG 2.1 AA 对比度，焦点可见，状态不能只依赖颜色，图标/图片有替代文本，所有关键操作可键盘完成。
- 验证视口：至少生成 1920×1080、1440×900、1024×768、768×1024、390×844 和 375×812 六组截图或视觉回归证据；必须定义像素差异阈值、动态区域豁免和人工批准记录，验收重点包括首屏信息密度、数据下方空隙、断点重排、溢出和主题切换前后布局一致性。
