## 1. 审核目的与当前边界

本包用于冻结 W1 的工程底座、质量门禁、契约/数据评审范围和后续模块的共同约束。W1 不交付业务页面或业务流程，不以空接口、空迁移、空 Topic、空消费者或 README 占位作为完成证据。

W0 服务接缝预留包已验证，但不等同于 W1 解锁。当前只允许执行 W1 Step 1；本包经用户审核通过后，才可进入 Step 2「契约、DDL 与技术设计」。

本模块遵循：

`Step 1 需求与验收 → Step 2 契约/DDL/技术设计 → Step 3 工程与后端门禁 → Step 4 工程底座前端/测试 → Step 7 完成留证`

W1 的 Step 4 只验收前端/测试工程底座、设计 Token 和可运行样例，不验收任何业务页面。

## 2. W1 范围

### 2.1 工程资产

1. GitHub Actions：后端、前端、契约、迁移、文档、敏感信息和差异检查纳入 PR 门禁。
2. 后端：Java 21、Maven 模块边界、传统业务模块分层、中文注释、统一 API、TraceId、审计和幂等基础。
3. 前端：pnpm workspace、Vue 3 + TypeScript + Vite + Pinia + Element Plus + ECharts 的工程入口；共享类型、API Client、设计 Token 和测试入口。
4. 测试：unit、integration、contract、e2e、performance、security 的可执行目录与最小运行入口。
5. 运行环境：Docker Compose 可重复启动的工程依赖、健康检查、资源限制、配置模板和敏感配置边界。
6. 数据库：Flyway 前向迁移入口、命名规则、Schema 所有权、迁移检查和回滚/补偿说明；不创建未经审核的业务迁移。
7. 契约：OpenAPI、AsyncAPI/JSON Schema、MQTT Topic/ACL 和版本兼容检查；契约为生成客户端和测试数据的唯一输入。
8. 文档：本包、Step 2 设计包、Runbook、质量门禁说明和本地链接均可追溯。
9. Kafka 工程跑道：以 Compose profile、共享客户端配置、事件信封、幂等/DLQ 测试工具、健康检查和契约校验接入工程底座；不创建业务 Topic、业务生产者或业务消费者。

### 2.2 必须完成逐字段评审的业务边界

W1 不实现以下业务，但必须形成字段、所有权、状态、索引、脱敏、审计和消息边界的评审结论：

| 领域 | W1 必须冻结的内容 | 后续使用模块 |
| --- | --- | --- |
| 个人身份 | 个人用户主档、渠道身份映射、冲突和幂等创建/更新 | W2、W6 |
| 个人资金 | 现金充值资金批次、原支付交易、商户路由、可退款余额、非现金权益隔离 | W6 |
| 订单结算 | 充电订单站点结算快照、锁单后调整、退款/补差的追加记录 | W5、W8 |
| V2G | 独立用户收益余额、模拟/关闭态、禁止提现事实 | W11 |
| 监管 | `ecosystem-service` 监管任务、目标路由、报送/补推/回执/对账状态 | W10 |
| Kafka | 公共消息封装、事件版本、幂等键、消费者组、重试和 DLQ 责任 | W2-W12 |

国内省市监管属于当前 W10 的 `ecosystem-service` 范围；虚拟电厂及其他第三方数据/调控能力仍为 W12 后独立审批范围，W1 不创建其 Topic、消费者、协议入口或页面。

### 2.3 Kafka 工程跑道集成边界

W1 要集成 Kafka 的工程能力，但不提前实现任何业务事件流。验收至少包括：

- Compose 中提供可重复启动的 Kafka 工程 profile、健康/就绪检查、资源限制和关闭说明；具体 broker 版本、端口和持久化策略在 Step 2 固定。
- 共享生产者/消费者配置：超时、重试退避、批量、手动提交、最大轮询间隔、消费者组命名和优雅停机。
- 公共事件信封和消息头：`eventId`、`eventType`、`eventVersion`、`occurredAt`、`traceId`、`idempotencyKey`、`producer`、租户/工作空间范围和 Schema 版本。
- 统一幂等、重试、DLQ、重放和人工处置接口；工程 Testkit 能验证重复投递、乱序、过期、失败重试和 DLQ 转移。
- Kafka readiness、积压/消费延迟、重试和 DLQ 指标，以及日志中的 TraceId、事件 ID 和脱敏约束。
- AsyncAPI/JSON Schema lint、兼容性检查和契约生成入口；没有登记在事件目录中的业务 Topic 不得创建。

本阶段允许工程测试 Topic 或隔离 Testkit，不允许创建 M1、P1、监管、V2G、VPP 或其他业务 Topic、生产者、消费者和运行时流程。

## 3. 明确不做事项

- 不创建 M1、P1 或其他业务页面、业务端点、业务消费者和业务 Topic。
- 不配置真实微信/支付宝/支付商户、生产通知或真实退款；只允许确定性 Mock 夹具。
- 不创建真实 V2G 放电、真实收益结算、提现申请、付款、回单或提现记录。
- 不创建 VPP/第三方外部生态控制能力，不赋予 `ecosystem-service` 设备控制权。
- 不改写既有 Flyway 迁移、已锁定账单、历史支付路由或历史商户事实。
- 不以空类、空迁移、空 Schema、假数据或“计划中”替代可执行门禁。

## 5. 多主题与响应式基线（待用户审核）

此前高保真稿仅作为外部视觉预览，未视为生产设计或验收证据。W1 只冻结可实现的设计 Token 和切换约束，不开发业务页面。

建议首批保留三个主题候选：

1. `energy-green`：浅色运营管理后台，以能源绿为主色。
2. `graphite-night`：深色监控工作台，以蓝黑和青色高亮为主色。
3. `command-deep`：深邃蓝数据大屏，以半透明面板和数据发光为主色。

三种主题必须满足：

- 同功能、同信息层级、同布局语义，仅替换 Token，不复制业务组件。
- 充电中、故障、离线、空闲等状态语义保持一致，状态色不得被主题任意改变。
- 以 1920×1080 为主验收视口，同时支持 1440、1024、768 及移动端自适应。
- 栅格为 24 列，间距为 8px 倍数；数字/金额使用等宽字体 Token。
- 支持高对比度、键盘可操作、表格横向滚动和移动端卡片化策略。
- 主题偏好保存范围、默认主题、权限无关性和恢复策略必须写入前端设计说明。

如用户不批准三个候选主题，Step 2 前应指定主题数量、名称和优先级；在此之前不生成主题业务页面。

### 5.1 排版、布局与响应式验收基线

主题只改变 Token，不改变信息架构和布局骨架。W1 必须先冻结以下可实现规则：

- 画布与容器：以 1920×1080 为主验收视口；桌面内容最大宽度 1440px 并居中，1440px 笔记本全宽；主容器内边距、卡片间距和栅格间距均为 8px 倍数。
- 栅格与骨架：24 列栅格、默认列间距 24px；运营后台采用侧栏 + 顶栏 + 内容区；侧栏默认 210px，折叠态 64px；顶栏、内容区最小高度和密度必须使用布局 Token。
- 排版：中文字体栈、H1/H2/正文/辅助文字字号与行高、数字/金额等宽字体、字重、截断和 Tooltip 规则必须定义为 Token，不在页面内散落硬编码。
- 信息密度：数据卡片按内容自适应高度，不用固定等高制造大块空白；表格行高、工具栏高度、分页间距、卡片内上下留白需有正常/紧凑两档。
- 断点重排：`>=1920` 居中最大宽度 1440；`1440–1919` 全宽布局；`992–1439` 保持侧栏展开并压缩列宽；`768–991` 侧栏折叠为 64px、表格横向滚动；`<768` 表格转卡片列表、双列转单列、操作区换行。
- 内容安全：标题单行省略、地址两行省略、数值不换行；窗口缩放不得出现横向溢出、遮挡、重叠或不可访问操作；空态/错误态/无权限态/禁用态仍保持相同骨架。
- 交互与可访问性：主题切换不改变布局，键盘焦点、Hover、禁用、加载和高对比度状态有明确 Token；触控目标和表格操作在移动端可完成。
- 验证视口：至少生成 1920×1080、1440×900、1024×768、768×1024、390×844 五组截图或视觉回归证据；验收重点包括首屏信息密度、数据下方空隙、断点重排、溢出和主题切换前后布局一致性。

## 6. 数据与权限责任冻结要求

Step 2 必须把以下内容落实到字段级设计，W1 不得用模糊的“公共表”或“共享数据库”替代：

- 每个字段的业务所有者、写入服务、读取服务、敏感等级、保留期和审计要求。
- 金额使用最小货币单位整数；时间统一 UTC 存储并明确展示时区。
- 个人身份、资金批次、订单结算快照、V2G 收益和监管任务分别定义生命周期和删除/归档边界。
- 每个 Kafka Topic 只有唯一发布者，消费者组、分区键、幂等键、重试和 DLQ 责任必须登记在事件目录。
- P1 不把 M1 应用生命周期、内容、业务开关或用户资格误实现为个人页面/功能权限。
- 外部连接器只保存脱敏配置和引用，不在代码、日志、导出或文档中保存凭据值。
